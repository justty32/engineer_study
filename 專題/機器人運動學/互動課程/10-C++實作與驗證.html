10 · 數學正確還要能被程式證明

C++ 實作契約、測試與除錯證據

真正難抓的錯通常不是矩陣乘法，而是「這個矩陣把哪個框架變到哪個框架、角度是度還是弧度、向量是點還是方向」沒有進入型別與測試。

白話定位：數學契約若只寫在開發者腦中，就像把資料庫 schema 拿掉後用幾個 double[16] 互傳。編譯器只看尺寸，不知道 frame、單位、時間與物理型別；本章要把這些隱含前提變成 API、測試與 log。

怎麼玩：先保留三個「靠人記住」的選項，看輸出列出哪些錯能靜默通過；再一次只改一項契約。最後全選顯式契約，觀察它仍不能替你證明幾何參數、碰撞或真機安全正確。

檢查 API 契約

struct JointState { std::array<Radian, 7> q; };
template<class From, class To> struct Transform;
Transform<ToolFrame, BaseFrame> forwardKinematics(const JointState&);

最小測試組

測試 能抓什麼
零角與單一關節 零位、軸方向、固定連桿平移與乘法順序
T·T⁻¹≈I、RᵀR≈I 逆變換、旋轉漂移與矩陣區塊錯誤
雅可比有限差分 關節軸／原點、叉積順序、框架錯配
FK→IK→FK IK 回傳解是否真正重建目標；不要要求 q 必須等於原 q
近奇異與極限案例 數值爆炸、停止條件、阻尼與夾限行為

每次迭代留下什麼證據

記錄迭代編號、位置／姿態誤差、最小奇異值或條件指標、阻尼、||Δq||、最接近的關節極限及停止原因。只記「IK failed」無法區分不可達、數值錯誤、框架錯誤或種子不佳。

一個容許值不能包辦所有量

假設 FK→IK→FK 的位置殘差為 8×10−5 m，也就是 0.08 mm；若任務容許 0.1 mm，位置通過。姿態殘差若為 0.002 rad≈0.115°，而容許 0.05°，姿態仍失敗。不能把兩者都拿去和 1e-3 比較，因為單位與任務意義不同。

浮點比較也要同時考慮絕對與相對尺度。例如很接近 0 的矩陣非對角元素適合絕對容許值；比較 1000 m 與 1000.001 m 時則可能需要相對容許值。但容許值必須來自數值分析與工程需求，不應為了讓測試變綠而放寬。

先把幾何語意變成型別

裸的 Vector3d 看不出是點、方向、角速度或哪個座標系。可用包裝型別或 template 標籤保存來源／目標 frame；角度輸入邊界接受度數時立即轉弧度，內部只保留一種單位。矩陣儲存的 row-major／column-major 與數學上左乘／右乘是不同問題，都要在介面文件寫清楚。

最小測試金字塔

  1. 代數：RᵀR≈I、det(R)≈1、T·T⁻¹≈I。
  2. 模型：零位與單關節 90° 可手算案例。
  3. 微分：雅可比每欄對有限差分，掃不同 ε。
  4. 求解：可達、不可達、奇異附近、多初值與關節極限案例。
  5. 系統：時間戳、座標轉換版本、控制週期與實機低速驗證。

log 要保存推理鏈

每次 IK 至少記錄目標 frame、目標位姿、初始 q、每步位置／姿態誤差、最小奇異值、阻尼、Δq、極限裁切與終止原因。只有「success=true」無法分辨是精確收斂、容許值過鬆或迭代上限剛好停止。

證據的層級與常見誤解

  • 單元測試：能證明指定輸入下的代數與契約符合預期，不能證明模型參數等於真機。
  • 模擬與 property test：能掃大量構型及不變量，仍可能與實作共享同一個錯誤慣例。
  • 回放 log：能重現軟體資料流；若時間戳或外參錯，重現的仍是錯誤資料。
  • 外部量測：可驗證真實工具位姿，但量測器本身也有校正、不確定度與同步邊界。

不要混淆 column-major 儲存與欄向量慣例、編碼器 count 與關節角、函式回傳成功與任務達成、以及 FK→IK→FK 通過與 IK 找回原 q。冗餘手臂本來就可能用不同 q 重建同一位姿。

浮點相等怎麼判？

用與量綱相符的絕對／相對容許值，例如位置公尺誤差與旋轉角誤差分開；不要對矩陣每格使用同一個魔法常數後就宣稱位姿正確。

「都是 double」就是最常見的痛點

編譯器允許把 90.0 傳給接受 rad 的函式，也允許把工具座標的 Vector3 加到基座座標的 Vector3。兩者記憶體形狀完全相容，物理語意卻錯。型別化不是為了漂亮，而是把原本要到真機偏移才發現的錯，在編譯或介面邊界提早攔下。

精確限制也要說清楚：強型別只能保證程式遵守你寫下的契約；若契約本身把相機外參方向定反，整套系統仍會一致地算錯。因此型別、手算案例、獨立實作與外部量測缺一不可。

一筆 transform 要帶哪些上下文？

至少包括來源 frame、目標 frame、數值、長度單位、時間戳與資料版本。靜態連桿 T 也應有模型版本；動態 TF 若差 20 ms，在工具高速移動時就可能造成明顯空間誤差。例如速度 0.5 m/s、時間錯位 0.02 s，位置會差約 0.5×0.02=0.01 m，也就是 10 mm。

若 log 只有最終 4×4，事後無法判斷它使用哪組 q、哪版工具偏移或哪個時間。可重現性要求保存輸入與契約，不只是輸出數字。

把測試失敗變成可定位訊息

不要只寫「matrix mismatch」。較有用的訊息是：「姿態正交誤差 2.1×10−8，門檻 1×10−9；位置殘差 0.34 mm，門檻 0.10 mm；最大差出現在 base→joint4 的平移欄」。這讓開發者知道是數值漂移、幾何誤差，還是哪一節開始錯。

一組具體容許值例子：位置需求 0.5 mm，量測器標準不確定度 0.1 mm，數值誤差只有 0.001 mm。測試門檻不能設成 0.001 mm 後要求真機通過，也不能因真機誤差較大就把純代數測試放寬到 0.5 mm；不同層級要各用自己的誤差預算。

最小可重現 IK log 範例應能回答什麼？
  • 目標位姿在哪個 frame、時間戳為何？
  • 初始 q、每步 q 與 Δq 是否用 rad？
  • 位置與姿態殘差各是多少、在哪個 frame？
  • J 的尺度、最小奇異值、λ 與裁切事件是什麼？
  • 停止是通過容許值、停滯、超時還是數值無效？

具備這些欄位，離線回放才可能重建推理鏈；仍須保存對應的模型參數與程式版本，否則同一 q 在新版模型可能得到不同 FK。

測試預言機不能與被測程式同源

若 production FK 與 test expected 都呼叫同一個旋轉函式，該函式符號寫反時測試仍可能通過。手算特殊角、幾何不變量、不同建模方法與外部量測提供不同來源的證據；來源愈獨立，共同錯誤愈不容易被遮住。

property test 可隨機檢查 RTR≈I、T 反向往返、連桿固定距離與 FK→IK→FK。它適合找邊界，但每次失敗要保存亂數種子與最小化案例，否則無法重現。

錯誤處理也是 API 契約

IK 不可達、最大迭代、NaN、關節超限要分開回報；不得在數值無效時仍回傳上一組 q 並標成功。呼叫端也要決定保持、退回、安全停止或換種子，數學函式不應自行假設真機安全策略。

能教別人的檢核：設計一筆可重現 log，讓另一位工程師不看原執行程序也能重建模型版本、輸入、每步誤差、裁切與停止原因。

一個 frame 型別測試的思考方式

若函式宣告 Transform<B,A> compose(Transform<B,C>, Transform<C,A>)，中間 C 才能接合；把 Transform<D,A> 傳入應在編譯期失敗。實際 template 參數順序可自訂，但必須與數學文件一致，並用一個故意不該編譯的測試保護契約。

序列化後型別資訊可能只剩字串，因此反序列化也要驗證 from、to、單位與版本。強型別保護記憶體內的 API，不會自動保護網路封包或舊 log。
