## 共通互動原則

- 所有操作以原生數值輸入、`select`、核取方塊與按鈕完成；不以拖放作為唯一操作。
- 數值欄位在 `input`／`change` 時即時計算；空值、非數字、無限大、除零或物理範圍錯誤時清除舊結果，並以文字說明原因。
- 每個模組使用 `data-module`、`data-nav`、`data-complete`、`data-reset-module`；狀態以固定符號、文字、邊框與顏色同時呈現。
- 動態回饋使用 `aria-live="polite"`。所有欄位有可見 `label`，按鈕使用 `type="button"`。
- 手機版不依賴寬表格或橫向拖曳；時間線、任務資料與檢查清單在 390px 容器內換行。

## 1. 架構抉擇：superloop 或 RTOS

### 互動機制

以五個情境輸入建立需求輪廓，畫面並列顯示 RTOS 分數與 bare-metal 分數，最後給出「建議 RTOS」、「建議 non-blocking superloop」或「需要原型量測」的 verdict。這是架構提示，不是任務數越多就必須使用 RTOS 的規則。

### 輸入／操作

- 使用數值欄位 `arch-task-count`、`arch-deadline-count`、`arch-blocking-flows`、`arch-ram-kb`、`arch-team-size`。
- 預設值為 3、2、2、64 KiB、2；使用者可逐項調整，並可用 `data-reset-module="architecture"` 還原。
- 顯示 `arch-rtos-score`、`arch-bare-score`、`arch-verdict`、`arch-status`、`arch-feedback`。

### 因果回饋

- 任務數至少 3、deadline 至少 2、阻塞流程至少 2，各自增加 RTOS 分數；團隊至少 2 人再增加一分。
- 任務數至多 2、沒有 deadline、沒有阻塞流程或 RAM 小於 16 KiB，分別增加 bare-metal 分數。
- RTOS 分數較高時顯示 RTOS；bare-metal 分數較高時顯示 non-blocking superloop；同分時提醒先做原型量測。

### 錯誤路徑

- 任務數、deadline、阻塞流程、團隊人數必須是非負整數；團隊人數至少為 1。
- deadline 不可大於任務數；RAM 必須大於 0。錯誤時清除分數與 verdict，不保留上一個有效結果。
- 回饋指出輸入限制與原因，不以「資料不足」取代具體欄位錯誤。

### 學習成果

能從任務量、截止期限、阻塞流程、RAM 與團隊維護成本說明架構選擇，理解 RTOS 的收益與每任務堆疊、同步複雜度等代價。

### 390px 注意事項

- 分數與 verdict 使用可換行的單欄 metric，不使用固定寬度表格。
- 五個輸入各自一列，label 與輸入框不並排擠壓；回饋文字可自然換行。

## 2. 非阻塞 event loop

### 互動機制

用四個步驟時間組成一圈 event loop，立即顯示 cycle、最壞回應、剩餘裕度與 busy share。畫面用簡單文字列或比例條表示時間組成，不新增拖曳或動畫操作。

### 輸入／操作

- 使用 `loop-sensor-ms`、`loop-protocol-ms`、`loop-log-ms`、`loop-busy-ms`、`loop-deadline-ms`。
- 預設為 2、3、1、0、10 ms；每個欄位可輸入 0 以上數值。
- 顯示 `loop-cycle-ms`、`loop-worst-response-ms`、`loop-slack-ms`、`loop-busy-share`、`loop-status`、`loop-feedback`。

### 因果回饋

- 將四個步驟相加得到 (T_{loop})，並以一圈近似事件剛好錯過一次服務時的最壞回應。
- 以 deadline 減去 cycle 得到 slack；busy 時間除以 cycle 得到 busy share，cycle 為 0 時 busy share 顯示 0.0%。
- cycle 超過 deadline 時顯示阻擋；busy 大於 0 即使期限通過也顯示警告，回饋指出可改用狀態機、timer、ISR、DMA 或可阻塞的 RTOS API。

### 錯誤路徑

- 四個步驟時間可為 0，但不可為負；deadline 必須大於 0。
- 空值或非有限數值時清除所有結果；不要把錯誤輸入當成 0。
- 對 cycle 為 0 的合法輸入走明確的 0.0% 分支，避免除零。

### 學習成果

能以最壞迴圈時間判斷非阻塞狀態機是否有足夠 deadline 裕度，並辨認 busy-wait 會如何侵蝕 CPU 與回應時間。

### 390px 注意事項

- 時間單位與結果數值分開放置，結果卡內允許數字換行。
- 四段時間的文字標籤採單欄排列；比例條只作輔助，不承擔唯一資訊。

## 3. ISR 延遲預算

### 互動機制

以事件發生後的延遲時間線呈現「關中斷區段 → 高優先 ISR → 進入成本 → 目標 ISR」，並同步計算起始延遲、總反應時間、headroom 與 ISR CPU load。

### 輸入／操作

- 使用 `irq-disabled-us`、`irq-higher-duration-us`、`irq-higher-count`、`irq-entry-us`、`irq-handler-us`、`irq-rate-hz`、`irq-deadline-us`。
- 預設為 12、18、2、2、15、1000、100（時間以 µs）；可修改後即時重算。
- 顯示 `irq-start-latency`、`irq-response-time`、`irq-headroom`、`irq-cpu-load`、`irq-status`、`irq-feedback`。

### 因果回饋

- 起始延遲由關中斷時間、高優先事件總時間與 ISR 進入成本組成；反應時間再加上目標 handler 時間。
- ISR CPU load 由 handler 時間與觸發頻率決定；response 超過 deadline 時阻擋，load 超過 20% 警告，超過 100% 阻擋。
- 通過回饋明確指出 ISR 只清旗標、取最少資料，再用 queue、semaphore 或 notification 交棒，不能在 ISR 中阻塞。

### 錯誤路徑

- 時間與 rate 可為 0；higher count 必須是非負整數；deadline 必須大於 0。
- 空值、負值、非有限值或計算結果為 Infinity 時清除舊結果並說明欄位原因。
- 反應時間或 CPU load 進入阻擋條件時，不得只以顏色標示，必須在 `aria-live` 回饋寫出超限原因。

### 學習成果

能建立基本 ISR 延遲與反應時間預算，理解高優先中斷、關中斷區段、handler 長度與觸發頻率之間的因果關係。

### 390px 注意事項

- 時間線改成垂直排列，每段顯示名稱、數值與單位；不要讓時間線依賴寬度固定的表格。
- status 與 feedback 放在結果區下方並可換行，避免數字與警告互相覆蓋。

## 4. Polling／interrupt／DMA

### 互動機制

讓使用者輸入資料量、速率、每 byte 成本、DMA setup 成本與 CPU 頻率，並列比較 polling 與 DMA 的 CPU 負載，顯示吞吐量、節省比例與選擇建議。

### 輸入／操作

- 使用 `io-bytes`、`io-rate`、`io-cycles-byte`、`io-dma-setup-cycles`、`io-cpu-mhz`。
- 預設為 256 bytes、500 次／秒、80 cycles／byte、800 cycles、80 MHz。
- 顯示 `io-throughput`、`io-polling-load`、`io-dma-load`、`io-cpu-saved`、`io-verdict`、`io-status`、`io-feedback`。

### 因果回饋

- polling 負載依資料量、速率與每 byte cycles 增加；DMA 負載只計每次傳輸的 setup cycles。
- 吞吐量以 bytes × rate / 1024 顯示 KiB/s，並以 polling 與 DMA 負載差異計算 CPU 節省。
- polling 超過 100% 時阻擋；polling 不超過 2% 且 bytes 小於 64 時可顯示 polling 足夠；其他較適合 DMA／interrupt-driven。

### 錯誤路徑

- bytes、rate 與 cycles 可為 0；CPU MHz 必須大於 0。
- 非有限值或負值時清除所有計算結果；polling load 超過 100% 時顯示超載原因。
- 回饋標明本題未計 bus contention、DMA 記憶體限制、cache coherency 與 driver setup latency，避免把教學估算當成完整效能保證。

### 學習成果

能從資料吞吐量與 CPU 成本選擇 polling、interrupt-driven 或 DMA，並知道實際驅動仍需檢查緩衝區、記憶體與快取條件。

### 390px 注意事項

- polling／DMA 兩個負載使用上下排列的結果列，避免比較表超出視窗。
- 單位與長小數值分離，數值容器允許換行；回饋採短段落而非長橫排提示。

## 5. RMS／EDF 與堆疊 RAM

### 互動機制

提供三個 task 的執行時間、週期與 stack 欄位，以及 kernel RAM 與 RAM budget；畫面同時回饋 utilization、RM bound、RMS／EDF 條件與堆疊 RAM 裕度。

### 輸入／操作

- 三組欄位為 `task1-c`／`task1-t`／`task1-stack`、`task2-c`／`task2-t`／`task2-stack`、`task3-c`／`task3-t`／`task3-stack`。
- 另有 `kernel-ram` 與 `ram-budget`；預設三個 task 分別為 ((1,5,512))、((1,10,768))、((2,20,1024)) ms／bytes，kernel RAM 2048 B、budget 16384 B。
- 顯示 `sched-utilization`、`sched-rm-bound`、`sched-rm-result`、`sched-edf-result`、`sched-ram-used`、`sched-ram-headroom`、`scheduler-status`、`scheduler-feedback`。

### 因果回饋

- 三個 task 的 (C_i/T_i) 相加得到 utilization；以固定三 task 的 RM bound 比較 RMS 充分條件，並以 100% 比較 EDF 條件。
- RAM used 為 kernel RAM 加三個 task stack；headroom 為 budget 減 used。
- utilization 超過 RM bound 時只說「未由充分條件保證」，不可直接宣稱不可排程；EDF 僅在 utilization 不超過 100% 時通過。RAM headroom 小於 0 時阻擋。

### 錯誤路徑

- C、T、stack 與 kernel RAM 不可為負；週期 T 必須大於 0，且 C 不可大於 T；RAM budget 必須大於 0。
- 空值、非有限值、零週期或超出物理範圍時清除舊結果並指出欄位。
- 通過結果仍提醒 blocking、jitter、context switch 與優先權需用 RTA／量測驗證，stack 需用 watermark 驗證。

### 學習成果

能做初步 RMS／EDF 可排程性檢查並估算 task stack 與 kernel RAM，理解充分條件不是完整即時性證明。

### 390px 注意事項

- task 輸入以三個獨立區塊呈現，每個區塊內欄位直向排列；不要要求手機使用者左右捲動寬表格。
- 結果拆成「排程」與「RAM」兩組，長 feedback 放在最後並允許斷行。

## 6. 同步與交棒

### 互動機制

以情境選擇題組合資料型態、來源、消費者數、同步原語、優先權繼承與 lock order，立即給出建議原語、阻擋原因與交棒回饋。

### 輸入／操作

- 使用 `select`：`sync-kind`、`sync-producer`、`sync-consumers`、`sync-primitive`、`sync-priority-inheritance`、`sync-lock-order`。
- 預設為 data、ISR、one、queue、yes、fixed；選項只使用契約指定值：event／data／shared-resource、ISR／task、one／many、notification／binary-semaphore／queue／mutex、yes／no、fixed／unordered／none。
- 顯示 `sync-verdict`、`sync-blocker`、`sync-status`、`sync-feedback`。

### 因果回饋

- ISR 不可使用 mutex 或任何會阻塞的路徑。
- data 必須使用 queue；shared-resource 必須使用 mutex 且 priority inheritance 為 yes。
- 單一 consumer 的 event 可使用 notification 或 binary semaphore；多 consumer event 在本教材簡化為 binary semaphore。
- unordered lock order 一律阻擋；沒有巢狀鎖時可使用 none。通過時提醒 ISR 使用 FromISR API、必要時喚醒高優先任務，並另行規劃 timeout。

### 錯誤路徑

- 每次 select 變更都重新評估組合，不沿用上一組 verdict 或 blocker。
- 發生 ISR＋mutex、data 非 queue、shared-resource 缺少優先權繼承或 unordered lock order 時，顯示具體第一個阻擋原因。
- 阻擋訊息不只改色；`sync-blocker` 與 `sync-feedback` 必須可由鍵盤與輔助技術讀取。

### 學習成果

能依事件、資料流與共享資源選擇 notification、semaphore、queue 或 mutex，並理解 ISR 不阻塞、優先權反轉與固定上鎖順序的關係。

### 390px 注意事項

- 每個 select 使用完整 label 並單欄排列；選項文字不可被裁切或以省略號隱藏。
- verdict、blocker 與 feedback 分開排列，長阻擋原因可換行且不壓住下一個控制項。

## 7. Tickless 與低功耗 break-even

### 互動機制

以一個週期內的 run、sleep 與 wake 三段時間計算睡眠時間、平均電流、睡眠占比、相對全程 run 節省率與 break-even interval。用文字時間條或數值列呈現，不加入額外功耗模型。

### 輸入／操作

- 使用 `power-run-ma`、`power-sleep-ua`、`power-wake-ma`、`power-wake-ms`、`power-active-ms`、`power-period-s`。
- 預設為 15 mA、20 µA、10 mA、5 ms、50 ms、10 s；所有時間與電流欄位可修改。
- 顯示 `power-sleep-time`、`power-average-current`、`power-sleep-share`、`power-saving`、`power-break-even`、`low-power-status`、`low-power-feedback`。

### 因果回饋

- 以 `period × 1000 − active − wake` 得到睡眠時間；每週期各階段的電流乘時間後除以週期，得到平均電流。
- 以平均電流相對全程 run 電流計算節省率；wake 成本與 run、sleep 電流差決定 break-even interval。
- active 加 wake 不超過 period 時才可評估；run 大於 sleep 時才有 break-even，否則顯示無解警告。
- 回饋提醒 tickless 只移除 tick 喚醒，仍需關周邊時脈、處理 GPIO 漏電並量測完整電流剖面。

### 錯誤路徑

- 電流與時間不可為負；run 與 period 必須大於 0；active 加 wake 不可超過 period。
- 空值或非有限值時清除舊結果；不把負睡眠時間當成 0 來掩蓋輸入錯誤。
- run 小於或等於 sleep 時保留可計算的平均值，但 break-even 顯示無解並說明原因。

### 學習成果

能用 duty cycle、喚醒成本與平均電流判斷低功耗模式是否值得，理解睡眠時間增加不等於整機電流必然下降。

### 390px 注意事項

- 以六列結果取代固定寬度時間表；數值和單位分離並允許長小數換行。
- sleep share、saving 與 break-even 各自獨立顯示，避免百分比與毫秒單位擠在同一列。

## 8. Watchdog、持久化與更新復原

### 互動機制

以情境選擇搭配七項復原檢查清單，依契約固定順序指出第一個尚未完成的 gate、下一步與目前完成數。清單是可鍵盤操作的核取方塊，提供立即回饋與單模組重設。

### 輸入／操作

- 情境使用 `reliability-case`，選項為 hang、brownout-write、update-loss、stack-overflow，預設 hang。
- 七個核取方塊使用 `data-reliability-check`：`reliability-watchdog`、`reliability-bor`、`reliability-safe-state`、`reliability-stack-monitor` 預設勾選；`reliability-atomic-write`、`reliability-ab-slot`、`reliability-rollback` 預設未勾選。
- 顯示 `reliability-first`、`reliability-second`、`reliability-count`、`reliability-next`、`reliability-status`、`reliability-feedback`。

### 因果回饋

- hang：先保留 watchdog reset cause／fault log，再查最後 heartbeat、ISR 與死結。
- brownout-write：先確認 BOR 與 safe state，再用雙區加 CRC／journal 做原子設定寫入。
- update-loss：先寫備援 slot 並驗證，再原子切換；啟動失敗時 rollback。
- stack-overflow：先看 watermark／guard，再調整 stack 或移除不受控配置。
- 依固定順序回報第一個未勾項；七項全勾才顯示復原 gate 通過。

### 錯誤路徑

- 情境切換時重新套用該情境的固定診斷順序，不能把上一情境的 first／second 文字當成目前答案。
- 未完成項目時顯示第一個未勾項與下一步，不把部分勾選誤報為 gate 通過。
- 全勾只代表本題的復原 gate 完成，不宣稱已完成 secure boot、安全更新或量產驗證；reset 後恢復契約預設值。

### 學習成果

能依 hang、brownout、更新中斷與 stack overflow 的故障證據安排復原順序，並理解 watchdog、BOR、原子寫入、A/B 與 rollback 各自處理的失效模式。

### 390px 注意事項

- 核取方塊清單採單欄，label 包含完整名稱與可換行的補充文字；點擊文字也應可勾選。
- first、second、next 與 feedback 依序排列，長診斷文字不使用固定高度或省略號。
