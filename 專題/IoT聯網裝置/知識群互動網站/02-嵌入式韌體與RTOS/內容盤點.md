## 1. 架構抉擇：裸機、superloop 與 RTOS

**模組鍵：** `architecture`

### 學習目標

- 能從任務數、deadline、阻塞流程、RAM 與團隊維護需求，說明採用 non-blocking superloop 或 RTOS 的理由。
- 理解 RTOS 是架構工具，不是功能數量的直接判定；簡單功能也可能需要明確的時序或阻塞模型，複雜功能也可能先用狀態機驗證。

### 核心概念／公式

- MCU 將 CPU、Flash、RAM 與周邊整合在有限資源內；bare-metal 常用 `while(1)` 主迴圈加中斷，RTOS 則以任務、優先權與阻塞 API 組織工作。
- RTOS 提示分數：task ≥ 3 加 2、deadline ≥ 2 加 2、blocking flow ≥ 2 加 2、team ≥ 2 加 1。
- bare-metal 提示分數：task ≤ 2 加 2、deadline = 0 加 1、blocking flow = 0 加 1、RAM < 16 KiB 加 2。
- RTOS 分數較高時建議 RTOS；bare-metal 分數較高時建議 non-blocking superloop；同分時要求原型量測。

### 假設邊界

- 任務數、deadline 數、阻塞流程數與團隊人數是架構提示的整數代理量，不是完整的可排程性證明。
- task、deadline、blocking、team 必須為非負整數，team 至少為 1；deadline 不可大於 task；RAM 必須大於 0。
- 不比較特定 RTOS 的核心大小、授權或驅動生態，也不代替完整 RTA。

### 常見錯誤

- 看到功能變多就直接加入 RTOS，卻沒有估算每任務堆疊與核心 RAM。
- 用 `delay()` 或忙等假裝是週期控制，讓主迴圈無法服務其他事件。
- 把「有 RTOS」誤當成「自動具備即時保證」，忽略優先權、阻塞、上下文切換與量測。

### 可操作任務

- 以預設輸入計算兩種架構分數，再各調整一個因素，觀察建議如何改變。
- 為一個「感測、記錄、喚醒」裝置寫出三個 superloop 狀態，並指出哪個需求會使 RTOS 更有價值。
- 用一段文字說明架構選擇仍需以原型量測驗證，而非只依分數。

## 2. 非阻塞 event loop

**模組鍵：** `event-loop`

### 學習目標

- 能以一圈最壞執行時間估算非阻塞 event loop 的回應能力。
- 能辨識 busy-wait 與阻塞式流程對其他事件的影響，並把長工作拆成狀態機步驟、計時器事件或背景搬移。

### 核心概念／公式

$$T_{loop}=T_{sensor}+T_{protocol}+T_{log}+T_{busy}$$

$$T_{slack}=T_{deadline}-T_{loop}$$

- 最壞回應假設事件剛好錯過一次服務，以一圈 `T_loop` 近似；busy share 為 `T_busy / T_loop`。
- 預設 `T_loop = 6.000 ms`、最壞回應 `6.000 ms`、slack `4.000 ms`、busy share `0.0%`，結果為通過。
- cycle 超過 deadline 時阻擋；busy 大於 0 即使期限通過，仍要警告並引導改用狀態機、timer、ISR、DMA 或可阻塞的 RTOS API。

### 假設邊界

- 四個步驟時間可為 0，但 deadline 必須大於 0；cycle 為 0 時 busy share 顯示 `0.0%`。
- `T_loop` 是教學近似，不包含快取、匯流排競爭、其他中斷、排程器切換或多事件佇列積壓。
- `protocol` 在此只代表抽象的本地處理步驟，不展開連線協定內容。

### 常見錯誤

- 在主迴圈中以 busy-wait 等 ADC、回應或固定延遲，導致 deadline 被其他工作拖過。
- 只看平均執行時間，不看單圈最壞時間與事件剛錯過服務的情境。
- 把「切成函式」誤認成非阻塞；函式內仍可能等待旗標或長時間輪詢。

### 可操作任務

- 逐一調高 sensor、protocol、log 與 busy 時間，找出 slack 由正變負的臨界點。
- 將一個「取樣 → 轉換 → 記錄」流程拆成狀態機事件，標出每次 loop 只做一小段的位置。
- 比較消除 busy 時間前後的 busy share，並寫出一個可由 timer 或 ISR 觸發的替代方案。

## 3. ISR 延遲預算

**模組鍵：** `interrupts`

### 學習目標

- 能把關中斷區段、高優先中斷、入口成本與 handler 執行時間拆成反應時間預算。
- 能說明 ISR 應短、快且不可阻塞，並把較重的工作交給主迴圈或 RTOS 任務。

### 核心概念／公式

$$T_{start}=T_{disabled}+N_{higher}T_{higher}+T_{entry}$$

$$T_{response}=T_{start}+T_{handler}$$

$$U_{ISR}=T_{handler}f_{IRQ}/10^6$$

- 預設 start `50.0 µs`、response `65.0 µs`、headroom `35.0 µs`、ISR CPU load `1.50%`，結果為通過。
- response 超過 deadline 或 ISR load 超過 100% 時阻擋；load 超過 20% 時警告。
- ISR 只做清旗標、取最少資料與通知；資料可交給 queue、semaphore 或 notification。

### 假設邊界

- 時間與 rate 可為 0；higher count 必須為非負整數；deadline 必須大於 0；CPU load 不可成為 Infinity。
- 預算只考慮規格列出的延遲項，不是完整硬體延遲模型；優先權、關中斷區段與管線仍要在目標 MCU 量測。
- 不在此展開特定 NVIC 暫存器或硬體安全機制。

### 常見錯誤

- 在 ISR 中做格式化輸出、等待周邊、動態配置或大段運算。
- 忘記以 `volatile`、原子操作或短臨界區保護 ISR 與任務共享的狀態。
- 只用 ISR handler 時間估算反應，漏掉關中斷、高優先中斷與入口延遲。

### 可操作任務

- 調高關中斷時間或高優先中斷數量，找出 headroom 變成負值的條件。
- 將一個「接收資料並解析」ISR 改寫成「清旗標、寫入緩衝區、通知任務」的三步驟描述。
- 分別設定低頻長 handler 與高頻短 handler，觀察相同 CPU load 下 response 的差異。

## 4. Polling、interrupt 與 DMA

**模組鍵：** `driver-io`

### 學習目標

- 能以資料量、資料率、每 byte CPU 週期與 CPU 頻率估算 polling 和 DMA 的 CPU 成本。
- 能依資料量與即時需求選擇 polling、中斷驅動或 DMA，理解環形緩衝區在 ISR 與任務間的解耦作用。

### 核心概念／公式

$$U_{poll}=\frac{BfC_b}{F_{CPU}}\times100\%$$

$$U_{DMA}=\frac{fC_{setup}}{F_{CPU}}\times100\%$$

- `F_CPU` 由 MHz 轉 Hz；throughput 為 `bytes × rate / 1024`，單位為 KiB/s。
- 預設 throughput `125.0 KiB/s`、polling `12.80%`、DMA `0.50%`、CPU 節省 `96.09%`，建議 DMA。
- polling > 100% 時阻擋；polling ≤ 2% 且 bytes < 64 時可顯示 polling 足夠；其他情況若 DMA 較低則建議 DMA／interrupt-driven。

### 假設邊界

- bytes、rate、cycles 可為 0，但 CPU MHz 必須大於 0。
- 教學計算不納入 bus contention、DMA 記憶體限制、cache coherency、驅動設定延遲與實際中斷負載。
- DMA 是周邊與記憶體間的搬移工具，不代表資料一定已完成同步或可立即被所有任務使用。

### 常見錯誤

- 小量、低速資料也無條件使用 DMA，忽略設定成本與除錯複雜度。
- 把 DMA 省下的 CPU 週期當成零成本，漏掉完成通知、緩衝區生命週期與資料一致性。
- polling 迴圈沒有 timeout，周邊異常時把整個韌體卡住。

### 可操作任務

- 以預設值先比較三種 I/O 模式，再將 bytes 降到 32、rate 降低，判斷何時 polling 已足夠。
- 將 bytes、rate 或每 byte 週期調高，觀察 polling 超過 100% 的阻擋條件。
- 為 UART 或 ADC 設計「DMA 搬移 → 完成通知 → 任務消費」的資料流文字規格。

## 5. RMS／EDF 與堆疊 RAM

**模組鍵：** `scheduler`

### 學習目標

- 能以任務執行時間與週期計算 CPU 利用率，理解 RMS bound 是充分條件而非必要條件。
- 能用 EDF 的利用率條件與堆疊 RAM 預算做初步篩檢，知道仍需 RTA、blocking、jitter 與 watermark 量測。

### 核心概念／公式

$$U=\sum_i C_i/T_i$$

$$U_{RM}=n(2^{1/n}-1)$$

- 本模組固定 `n = 3`。預設 utilization `40.00%`、RM bound `77.98%`，RMS 充分條件與 EDF 條件皆通過。
- 預設 RAM used `4352 B`、headroom `12032 B`；RAM used 包含三個 task stack 與 kernel RAM。
- `U ≤ U_RM` 顯示 RMS 充分條件通過；超過 bound 只能顯示「未由充分條件保證」，不可直接宣稱不可排程。EDF 只有 `U ≤ 100%` 才通過。

### 假設邊界

- C、T、stack、kernel RAM 可為非負值，但 T 必須大於 0 且 C ≤ T；RAM budget 必須大於 0。
- 計算忽略 blocking、優先權配置、context switch、jitter、ISR 與共享資源造成的延遲。
- stack 數值是預算值，不是實際峰值；正式設計要以 watermark 或 guard 驗證。

### 常見錯誤

- 把 RM bound 當作所有可排程任務的硬上限，或把超過 bound 直接判定為不可排程。
- 只加總 task stack，忘記 kernel RAM、ISR 使用與其他靜態配置。
- 用平均執行時間代替 WCET，讓 utilization 看似通過但最壞情況失敗。

### 可操作任務

- 調高任一 task 的 C，觀察 utilization、RM 結果與 EDF 結果的差異。
- 將某個 task 的 C 調到大於 T，體驗物理範圍錯誤；再讓 RAM budget 小於 used，觀察阻擋。
- 在 RAM 預算中為 ISR buffer 與 log buffer 保留空間，說明為何不能只看 task stack。

## 6. 同步與交棒

**模組鍵：** `synchronization`

### 學習目標

- 能依事件、資料或共享資源選擇 notification、binary semaphore、queue 或 mutex。
- 能辨識 ISR 不可阻塞、priority inversion 與 deadlock 的邊界，建立「ISR 產生事件，任務消費工作」的交棒模型。

### 核心概念／判斷

- ISR 不可使用 mutex 或任何會阻塞的路徑。
- `data` 必須使用 queue；`shared-resource` 必須使用 mutex，且 priority inheritance 必須為 yes。
- 單一 consumer 的 event 可用 notification 或 binary semaphore；多 consumer event 使用 binary semaphore（本教材簡化）。
- lock order = unordered 一律阻擋；沒有巢狀鎖時可使用 none。
- 通過回饋須指出 ISR 使用 FromISR API，必要時喚醒較高優先任務；primitive 不能取代固定 lock order 與 timeout 策略。

### 假設邊界

- `sync-kind`、producer、consumer、primitive、priority inheritance 與 lock order 是教學用情境選擇，不是完整 RTOS API 相容性矩陣。
- 本模組只討論核心同步原語，不展開特定 RTOS 的記憶體模型、事件群組實作或驅動協定。
- queue、semaphore 與 notification 的容量、逾時與背壓仍需在實際資料流中另行設計。

### 常見錯誤

- ISR 直接拿 mutex、呼叫可能睡眠的 API，或把大量處理留在中斷上下文。
- 用 semaphore 傳遞需要保留內容的資料，造成資料遺失或共享緩衝區競爭。
- 多把鎖沒有固定順序，或只依 priority inheritance 就以為不會死結。

### 可操作任務

- 依序切換 event、data、shared-resource 三種情境，選出 primitive 並閱讀阻擋原因。
- 將 producer 從 ISR 改成 task，觀察哪些 API 限制消失、哪些資料競爭仍存在。
- 把 lock order 改成 unordered，再改回 fixed，描述 deadlock 風險如何改變。

## 7. Tickless 與低功耗 break-even

**模組鍵：** `low-power`

### 學習目標

- 能從 run、sleep、wake 電流與每週期時間估算平均電流、睡眠占比與節省率。
- 能用 break-even 判斷進入睡眠是否值得，並理解 tickless 只是減少 tick 喚醒，仍須處理周邊、GPIO 與電源域。

### 核心概念／公式

- `I_sleep` 由 µA 轉 mA；`T_sleep = period × 1000 − active − wake`。
- 每週期平均電流：

$$I_{avg}=\frac{I_{run}T_{active}+I_{sleep}T_{sleep}+I_{wake}T_{wake}}{T_{period}}$$

- 相對全程 run 的節省率為 `1 − I_avg / I_run`。
- break-even sleep interval：

$$T_{break-even}=\frac{I_{wake}T_{wake}}{I_{run}-I_{sleep}}$$

- 預設 sleep `9945 ms`、average 約 `0.100 mA`、sleep share `99.45%`、saving 約 `99.33%`、break-even 約 `3.34 ms`。

### 假設邊界

- 電流與時間不可為負；run、period 必須大於 0；active + wake 不可超過 period。
- 若 run ≤ sleep，break-even 無解並警告；結果是假設週期電流固定的教學平均，不是完整電池壽命預測。
- 不納入電池內阻、穩壓器靜態電流、喚醒後額外初始化、漏電或無線發射剖面。

### 常見錯誤

- 只看 MCU 的 sleep 電流，忘記感測器、電源域、LED、上拉電阻與穩壓器仍可能耗電。
- 把 active time 和 wake time 重複計入，或讓兩者總和超過週期。
- 以為啟用 tickless 就等於整機進入最低功耗，沒有確認喚醒源與周邊時脈。

### 可操作任務

- 調整 sleep 電流與 active time，觀察平均電流和 sleep share 的變化。
- 增加 wake time，找出 wake 成本使 break-even 變大的原因。
- 為一個週期性取樣裝置列出 Run、Sleep、喚醒源與要關閉的周邊，再寫出需要量測的電流剖面。

## 8. Watchdog、持久化與更新復原

**模組鍵：** `reliability`

### 學習目標

- 能依 hang、brownout-write、update-loss 與 stack-overflow 情境，先保留故障證據，再選擇復原動作。
- 能理解 watchdog、BOR、safe state、stack monitor、原子寫入、A/B slot 與 rollback 在復原流程中的位置。

### 核心概念／判斷

- hang：先保留 watchdog reset cause／fault log，再查最後 heartbeat、ISR 與死結。
- brownout-write：先確認 BOR 與 safe state，再用雙區加 CRC／journal 做原子設定寫入。
- update-loss：先寫備援 slot 並驗證，再原子切換；啟動失敗時 rollback。
- stack-overflow：先看 watermark／guard，再調整 stack 或移除不受控配置。
- 七個檢查項為 watchdog、BOR、safe state、stack monitor、atomic write、A/B slot、rollback；固定順序回報第一個未勾項，七項全完成才顯示復原 gate 通過。

### 假設邊界

- checklist 是故障處理順序的教學模型，不代表特定 bootloader、Flash 控制器或 RTOS 的完整實作。
- 通過復原 gate 不代表完成 secure boot、安全更新、簽章信任鏈或量產驗證。
- 不延伸到連線下載協定、金鑰管理、法規與功能安全認證。

### 常見錯誤

- watchdog 只會重置，卻沒有記錄 reset cause、heartbeat 或 fault log，導致重啟後無法追查。
- 將 brownout 時的半寫入設定當成有效值，沒有採用雙區、校驗或 journal。
- 更新直接覆蓋目前可開機映像，沒有備援 slot、驗證與 rollback。
- 只增加 stack 大小，沒有先用 watermark 或 guard 找出峰值與失控配置。

### 可操作任務

- 依序選擇四種 failure case，逐項勾選修復措施，觀察第一個未完成項與 gate 狀態。
- 讓 `update-loss` 保持 A/B 或 rollback 缺口，說明為何只能停在未通過。
- 為一次 hang 事件列出最小故障證據：reset cause、最後 heartbeat、目前任務與 ISR／鎖狀態。
