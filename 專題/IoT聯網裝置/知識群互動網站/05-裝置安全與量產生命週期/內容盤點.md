## 1. `threat-model`：威脅面初篩

### 來源與可追溯章節

- `BUILD-SPEC.md` §2「威脅面初篩」：四個輸入、決策優先序、輸出欄位與初篩警告邊界。
- [E5](../../../../電機/09-嵌入式特化/E5-IoT與邊緣運算.md) §8「IoT 資安」：裝置、通訊、身分、雲端與更新的縱深防禦。
- [E5](../../../../電機/09-嵌入式特化/E5-IoT與邊緣運算.md) §7「佈建、維運與裝置生命週期」：機群管理、OTA、退役。

### 核心概念

- 威脅判斷至少要同時看攻擊向量（遠端／實體／供應鏈）、影響（資料／控制／安全）、規模（單機／機群）與是否可更新。
- `update=none` 時，可維護性是最高缺口；不能只談初始防護。
- 供應鏈優先保護簽章 artifact 與信任根，再處理產線站授權與 audit；實體攻擊先處理不可匯出金鑰，再處理 secure boot／debug lock。
- 遠端機群優先每裝置身分與雙向認證，再處理撤銷／隔離／簽章 OTA；一般遠端情境先 TLS 身分驗證，再最小權限與更新。

### 常見誤解

- 「有 TLS 就完成 IoT 資安」：TLS 解決通道保護的一部分，不等於裝置身分、開機信任、更新或後端授權完整。
- 「威脅優先級就是完整 threat model」：此互動只做初篩警告，不涵蓋資產清冊、攻擊樹、控制驗證或風險量化。
- 「影響是資料就不需要安全狀態」：控制與安全影響仍須檢查失效行為；`safety` 會要求 safe state 與故障證據。

### 模型邊界

- 只輸出第一、第二控制與提示，不宣稱風險已接受、設計已合規或完成正式威脅建模。
- 不能由四個選項推導實際攻擊機率、損失金額、法規適用性或特定產品的安全等級。

### 回饋素材

- 操作：切換四個輸入，立即更新 `threat-priority`、`threat-first-control`、`threat-second-control` 與 `threat-feedback`。
- 判準：先指出決策順序命中的條件，再說明為何第二控制仍不可省略。
- 故障診斷句：沒有更新能力時，缺口不是「多加一層加密」，而是事件發生後無法修補。

## 2. `device-identity`：每裝置身分 gate

### 來源與可追溯章節

- `BUILD-SPEC.md` §3「每裝置身分 gate」：六項固定順序、預設勾選、情境輸出與通過邊界。
- [E5](../../../../電機/09-嵌入式特化/E5-IoT與邊緣運算.md) §8.1：每裝置唯一身分、憑證、雙向認證與 KMS/HSM。
- [量產：測試與法規認證](../../量產-測試與法規認證.md) §2–§3：序號／MAC／憑證寫入與產線 provisioning。

### 核心概念

- 身分閉環順序：唯一身分 → 私鑰不可匯出 → 憑證信任鏈 → 雙向認證 → 旋轉 → 撤銷。
- 六項皆是必要能力；總勾選數不能抵銷前面的第一缺口。
- 產線寫入的序號、MAC、金鑰與憑證必須能和裝置、後端與測試紀錄正確綁定。

### 常見誤解

- 「唯一序號就是身分安全」：識別值不等於持有不可匯出的私密憑證，也不等於後端授權。
- 「有憑證就不需撤銷與旋轉」：憑證會過期、洩漏或需分批替換，生命週期能力是閉環的一部分。
- 「六項勾五項已經足夠」：gate 以第一缺口回報，不用總分掩蓋必要項。

### 模型邊界

- 通過只代表身分生命週期有基本設計閉環；仍不代表 KMS/HSM 配置、憑證政策、後端授權與實機測試完成。
- 不在本模組推導密碼學演算法、憑證有效期或實際 PKI 拓撲。

### 回饋素材

- 操作：逐項勾選六個 `data-identity-check`，觀察第一缺口、第二提示、計數與狀態。
- 判準：缺少前項時，後項不能把 gate 變成通過；全部具備才顯示基本閉環。
- 跨層提示：產線 provisioning 的「唯一序號」要接到本模組的唯一身分，但不能取代金鑰保護。

## 3. `secure-boot`：Secure boot 鏈

### 來源與可追溯章節

- `BUILD-SPEC.md` §4「Secure boot 鏈」：四種情境、七項固定順序、必要項與 CRC 邊界。
- [E3](../../../../電機/09-嵌入式特化/E3-嵌入式韌體與驅動.md) §5「開機鏈與 Bootloader」：bootloader、映像驗證與記憶體分割。
- [E3](../../../../電機/09-嵌入式特化/E3-嵌入式韌體與驅動.md) §10「資安基礎」：secure boot、除錯介面鎖定、金鑰與防回滾。

### 核心概念

- 信任鏈順序：不可變根／根金鑰 → bootloader 簽章 → application 簽章 → 防回滾 → debug lock → fail closed → signed recovery。
- `normal` 與 `tampered-image` 需根、兩層簽章、fail closed、recovery；`downgrade` 另需 anti-rollback；`debug-attach` 另需 debug lock。
- CRC 只能抓意外損壞；數位簽章才處理真實性與未授權映像。
- debug lock 不可阻斷授權 recovery，否則量產後維修與復原會互相衝突。

### 常見誤解

- 「CRC 通過就是安全」：完整性校驗不會證明映像來自可信簽署者。
- 「只驗 application 就有 secure boot」：未驗證的 bootloader 可改寫信任根或跳過後續檢查。
- 「鎖死 JTAG 就完成安全開機」：debug lock 只是實體入口控制，不取代簽章鏈與失敗處理。

### 模型邊界

- 互動檢查的是設計證據存在與否，不驗證實際硬體 root of trust、密鑰儲存、簽章演算法或 recovery 映像。
- 不把 gate 通過解讀為韌體無漏洞、裝置不可逆向或已完成量產安全設定。

### 回饋素材

- 操作：切換 `normal`、`tampered-image`、`downgrade`、`debug-attach`，逐項補齊七個 checkbox。
- 判準：先回報固定順序中的第一缺口，再顯示情境所需的第二缺口；解釋該缺口如何阻止未授權開機或安全復原。
- 反例：把 CRC 勾成唯一防護時，回饋指出攻擊者仍可製作「CRC 正確但未簽章」的映像。

## 4. `ota-budget`：A/B OTA 容量與傳輸預算

### 來源與可追溯章節

- `BUILD-SPEC.md` §5「A/B OTA 容量與傳輸預算」：輸入、公式、預設值、驗證規則與排除項。
- [E3](../../../../電機/09-嵌入式特化/E3-嵌入式韌體與驅動.md) §6：A/B／雙 bank、簽章、斷電安全與版本管理。
- [韌體：架構與電源管理](../../韌體-架構與電源管理.md) §7「OTA 與版本」：備援區、驗證、回滾與斷點續傳。

### 核心概念

- 必要容量：`required = boot + image × slots + scratch + config`。
- 餘裕：`headroom = flash − required`；傳輸量：`transfer = image × delivery factor`；傳輸時間：`time = transfer / rate`。
- 規格預設值：`required = 1720 KiB`、`headroom = 328 KiB`、`transfer = 840 KiB`、`time = 52.5 s`。
- `slots < 2` 即使容量足夠，也要警告沒有 A/B rollback；負值、零速率、非整數 slots 等輸入要清除舊結果。

### 常見誤解

- 「Flash 放得下映像就有 A/B OTA」：還要放 boot、兩個 slot、scratch 與設定區。
- 「傳輸時間就是更新完成時間」：此模型只用映像量、傳輸倍率與速率估算，不含寫入、驗證、重試與重開機。
- 「兩個 slot 自動代表能安全回滾」：容量配置是必要條件，不代表切換、健康確認與回滾邏輯已實作。

### 模型邊界

- 不含檔案系統、對齊、delta update、TLS／協定 overhead、斷點續傳、flash wear 與真實網路功耗。
- 這是靜態容量與傳輸預算，不是實機效能、電池壽命或 OTA 成功率保證。

### 回饋素材

- 參數實驗：改變 flash、image、slots、delivery factor、rate，立即更新四個計算輸出與 verdict。
- 判準：至少測預設值、`headroom < 0`、`slots = 1`、`rate = 0`；說明阻擋原因而非只顯示錯誤。
- 計算交叉驗算：`128 + 700×2 + 128 + 64 = 1720`，`2048 − 1720 = 328`，`700×1.2 ÷ 16 = 52.5 s`。

## 5. `update-recovery`：更新故障復原 gate

### 來源與可追溯章節

- `BUILD-SPEC.md` §6「更新故障復原 gate」：四種失敗情境、八項順序與各情境必要項。
- [E3](../../../../電機/09-嵌入式特化/E3-嵌入式韌體與驅動.md) §6：完整性／真實性、A/B、斷電安全與回滾。
- [韌體：架構與電源管理](../../韌體-架構與電源管理.md) §5–§7：看門狗、已知安全狀態、持久化、A/B OTA 與版本。
- [E5](../../../../電機/09-嵌入式特化/E5-IoT與邊緣運算.md) §7–§8：OTA、機群管理、監控與縱深防禦。

### 核心概念

- 固定順序：簽章真實性 → integrity/hash → inactive slot → atomic switch → boot health confirmation → rollback → staged rollout/pause → observability。
- 斷電要保護寫入與切換原子性；首開失敗要能健康確認並回滾；機群回歸要能分階段、暫停並觀測。
- `signature-fail` 仍需 observability，因為拒絕更新本身是可運維事件。

### 常見誤解

- 「有簽章就能安全更新」：簽章處理真實性，不能單獨處理斷電、切換、首開失敗或機群回歸。
- 「A/B 等於自動回滾」：還需要 atomic switch、health confirmation 與 rollback 策略。
- 「OTA 任務顯示成功就是恢復成功」：要以裝置健康證據與服務恢復驗證為準。

### 模型邊界

- gate 只表示失敗處理路徑是否有基本閉環，不表示韌體沒有漏洞或更新內容本身正確。
- 不模擬實際斷電時序、bootloader 狀態保存、健康指標定義、分批比例或監控平台。

### 回饋素材

- 操作：切換 `power-loss`、`signature-fail`、`first-boot-fail`、`fleet-regression`，觀察情境化必要項。
- 判準：例如 `power-loss` 缺 atomic switch 時，回饋指出「備區存在」仍不足以保證斷電不變磚。
- 跨層診斷：把 E3 的 A/B／回滾接到 E5 的機群 staged rollout 與 observability，而非只停留在單機 bootloader。

## 6. `provisioning-line`：產線佈建 gate

### 來源與可追溯章節

- `BUILD-SPEC.md` §7「產線佈建 gate」：三種情境、八項固定順序、必要項與秘密保存限制。
- [量產：測試與法規認證](../../量產-測試與法規認證.md) §2–§3：DFT、產測韌體、燒錄、序號／MAC／金鑰／憑證、追溯 log。
- [E5](../../../../電機/09-嵌入式特化/E5-IoT與邊緣運算.md) §7：出廠注入身分／金鑰／憑證與 zero-touch 註冊。
- [E3](../../../../電機/09-嵌入式特化/E3-嵌入式韌體與驅動.md) §10：安全元件／OTP 與量產後 debug lock。

### 核心概念

- 固定順序：station authorization → unique serial/MAC → non-exportable key → certificate binding → readback/online challenge → failure quarantine → audit trace → debug lock。
- 新機與重工八項皆必要；憑證輪替不要求 debug lock，但不得解鎖已鎖裝置。
- 失敗品必須隔離，不得進下一站；log 不可保存能重建私鑰的明文秘密。

### 常見誤解

- 「產線有燒錄成功訊息就完成 provisioning」：還要驗證身分綁定、線上 challenge、失敗隔離與 audit。
- 「重工可直接重用原金鑰」：重工是高風險分支，需重新確認站點授權、綁定與追溯，不能讓失敗品流出。
- 「把私鑰寫進 log 方便除錯」：這會破壞不可匯出與後續撤銷／輪替的安全邊界。

### 模型邊界

- 不定義特定 HSM、KMS、站點網路拓撲、憑證格式或供應商工具；只檢查流程證據與順序。
- gate 通過不代表產線良率、治具能力、實際密鑰零知識流程或後端註冊服務已驗證。

### 回饋素材

- 操作：切換 `new-device`、`rework`、`certificate-rotation`，逐項檢查八個 `data-provisioning-check`。
- 判準：用「第一缺口」回報，並針對 quarantine、audit、debug lock 說明下一站或出貨風險。
- 故障案例：readback／online challenge 失敗時，結果應引導至 quarantine，而不是要求人工放行。

## 7. `production-gate`：EVT 到 MP 證據 gate

### 來源與可追溯章節

- `BUILD-SPEC.md` §8「EVT 到 MP 證據 gate」：四階段、八項證據、固定順序與各階段最低要求。
- [量產：測試與法規認證](../../量產-測試與法規認證.md) §1「從打樣到量產的階段」：EVT、DVT、PVT、MP 定義。
- 同筆記 §2–§4：DFT、ICT／FCT、RF／EMC、provisioning、追溯與法規認證。
- [E3](../../../../電機/09-嵌入式特化/E3-嵌入式韌體與驅動.md) §9：單元測試、HIL、靜態分析與除錯證據。

### 核心概念

- 固定順序：test points/SWD → ICT/FCT → secure boot/OTA evidence → RF/EMC prescan → production fixture → provisioning → traceability → change control。
- EVT 需前兩項；DVT 需前四項；PVT 需前七項；MP 八項皆需。預設 DVT 第一缺口是 secure boot/OTA evidence。
- 早期在 schematic／選料與設計階段預留測試點、治具可達性、認證策略與天線／EMC 對策，可降低後期重測成本。

### 常見誤解

- 「EVT 能開機就接近量產」：EVT 只要求最小測試可達性與功能驗證，尚不代表可靠度、認證或產線可重複。
- 「買預認證模組就不必做整機測試」：天線、整機 EMC、安規與整合條件仍可能需要驗證。
- 「MP gate 通過就是良率達標、認證完成、可直接出貨」：規格明確把這些排除在學習 gate 外。

### 模型邊界

- 只判斷階段證據是否具備，不計算良率、成本、認證通過率或製程能力指標。
- 不替代 FCC、CE、NCC 等正式測試、文件審查與市場法規判定。

### 回饋素材

- 操作：切換 `EVT`、`DVT`、`PVT`、`MP`，檢查八個 `data-production-check`。
- 判準：階段越後面，必要證據單調增加；顯示該階段的第一、第二缺口及為何尚不可前進。
- 取捨題：選預認證模組可降低無線認證負擔，但仍要保留整機 EMC、天線條件與文件追溯。

### 核心概念

- 固定順序：identify scope → quarantine → revoke identity → rotate affected credentials → patch → verify recovery → wipe local data → retain audit evidence。
- `compromised` 要能識別、隔離、撤銷、輪替、修補、驗證與保留 audit；`certificate-expired` 聚焦識別、輪替、驗證、audit；`lost-device` 聚焦識別、隔離、撤銷、audit；`retire` 聚焦識別、撤銷、清除、audit。
- 退役同時處理後端身分與裝置本地資料；恢復服務前需驗證，不只看任務狀態。

### 常見誤解

- 「刪除雲端裝置紀錄就是退役」：本地資料、憑證與私有身分仍可能存留。
- 「修補成功就能解除隔離」：要先驗證恢復，並保留事件範圍與處置證據。
- 「遺失裝置只要遠端 wipe」：若裝置離線，仍需先隔離與撤銷身分，避免重新上線冒認。

### 模型邊界

- 互動是事件處置順序的 gate，不是 SIEM、憑證服務、MDM 或安全回應平台的實際操作。
- 不定義資料保留期限、wipe 的硬體保證、修補內容或事件嚴重度分級；這些需產品與法規政策另訂。

### 回饋素材

- 操作：切換 `compromised`、`certificate-expired`、`lost-device`、`retire`，逐項填入八個 `data-lifecycle-check`。
- 判準：事件至少顯示第一、第二缺口；`retire` 缺 `wipe` 時明確指出只撤銷後端身分仍未清除本地資料。
- 跨層整合：把裝置身分的 revoke／rotate 接到 provisioning 的憑證綁定與 OTA 的 patch／verify，形成從製造到退役的生命週期閉環。

## 跨模組回饋素材與一致性檢查

- **取捨判斷**：`threat-model` 比較遠端、實體、供應鏈與機群優先控制；`production-gate` 比較預認證模組的時間／成本節省與整機驗證責任。
- **參數實驗**：`ota-budget` 使用預設值、空間不足、單 slot、零速率與非整數 slots；所有錯誤都清除舊結果。
- **故障診斷**：`secure-boot`、`update-recovery`、`provisioning-line`、`fleet-lifecycle` 都以「第一缺口＋為什麼」回饋，不用總數掩蓋必要項。
- **跨層整合**：身分（device identity）支撐 provisioning 與 fleet revoke；secure boot 與 OTA budget 支撐 update recovery；production gate 提供前述安全能力的階段證據。
- **共同邊界**：所有 gate 都是學習模型或設計證據初篩，不是正式安全認證、法規認證、量產放行或實機安全保證。
- **用語一致**：`簽章`處理真實性，`CRC／hash`處理完整性或損壞檢查，`撤銷`處理失效身分，`回滾`處理更新後失敗；四者不可互換。
