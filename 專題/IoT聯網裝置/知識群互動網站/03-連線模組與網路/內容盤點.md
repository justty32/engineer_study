## 整體承載邊界

- 目標讀者：軟體能力較強、但需要從裝置端接合角度重新建立連線模組與網路判斷力的學習者。
- 完成後能做的事：初篩連線 bearer、估算 host 介面容量、分流 AT/URC、設計有上限的重連、按層重建會話、估算資料與 keepalive 預算，並安排模組故障升級。
- 互動計算都是簡化的教學預算；正式設計仍需查模組 manual、電信商條件、封包擷取、網路量測與實機功耗剖面。
- 聚焦 MCU host 與外購通訊模組的接合，不實作 Wi-Fi、蜂巢式或 LPWAN 的 PHY/MAC。
- MQTT、CoAP、TCP、TLS 只保留裝置端選擇、成本與會話前置條件，不重述軟體本科的完整協定內容。
- 天線、匹配、link budget、EMC 與法規留給 RF 知識群；TLS 憑證信任、secure element、佈建、退役與安全更新留給安全量產知識群。
- 所有模組都應用文字、公式、狀態與明確回饋呈現，不依賴圖片或外部資源。

## 模組 1：Bearer 選型與連線取捨

**模組鍵：** `bearer-choice`

### 學習目標

- 能從距離、payload 大小、供電方式、基礎設施擁有者與下行頻率做第一輪 bearer 篩選。
- 能說明 BLE、Wi-Fi、Thread、LoRaWAN、NB-IoT、LTE-M 等選項在頻寬、功耗、覆蓋與部署成本間的取捨。
- 知道選型結果只是初篩，仍需以實際覆蓋、月租或自建成本、認證與場域測試確認。

### 核心概念與判斷

- 距離範圍：`room`、`campus`、`wide`；資料量：`small`、`medium`、`high`；供電：`coin`、`battery`、`mains`。
- 基礎設施：`private` 或 `operator`；下行需求：`rare` 或 `frequent`。
- 決策順序固定為：
  - `high` payload 且 `wide` → LTE-M。
  - `high` payload 且非 `wide` → Wi-Fi。
  - `wide`、`operator`、`frequent` → LTE-M。
  - `wide`、`operator`、`rare` 或 `small` → NB-IoT。
  - `wide`、`private` → LoRaWAN。
  - `campus`、`small`、`private`、`rare` → LoRaWAN。
  - `campus`、`private` → Thread。
  - `room`、`coin` → BLE。
  - 其餘 → Wi-Fi。
- 預設值應得到 NB-IoT，runner-up 為 LTE-M；回饋必須說明這不是認證、覆蓋或成本保證。

### 假設與適用範圍

- 選項是教學用代理變數，不代表每種技術的所有速率、頻段或模組實作。
- 「wide」不等於任何地點都能覆蓋；「operator」也不等於一定可取得服務。
- 不在此做 RF link budget、天線設計、法規或安全佈建判定。

### 常見錯誤模式

- 只看最大吞吐量，忽略電池壽命、下行可達性與部署模式。
- 看到長距離就直接選蜂巢式，沒有區分私有部署與電信商服務。
- 把初篩結果當成實機驗證或認證結論。

### 可操作任務

- 逐一切換距離、payload、供電、基礎設施與下行需求，觀察 verdict、runner-up 與 trade-off。
- 將「小資料、電池、偶爾下行」與「寬頻、主電、頻繁下行」兩種情境比較，寫出選擇理由。
- 找出一組輸入，使 runner-up 與主選項互換，並指出仍需量測的未知條件。

## 模組 2：Host 介面容量與流量控制

**模組鍵：** `host-link`

### 學習目標

- 能把 UART baud rate 換成有效 byte/s，並比較 steady traffic、burst traffic 與 buffer 容量。
- 能判斷何時需要 RTS/CTS、DMA、環形緩衝或更快的 SPI/SDIO/USB 介面。
- 能區分「平均速率足夠」與「突發期間接收端會溢位」這兩種不同問題。

### 核心概念與公式

- UART 有效容量：

  $$R_{UART}=\frac{baud}{bits_{byte}}$$

- 穩態資料率：

  $$R_{steady}=payload\times message\_rate$$

- 利用率、突發超額與緩衝餘裕：

  $$U=\frac{R_{steady}}{R_{UART}}$$

  $$B_{excess}=max(0,(R_{burst}-R_{UART})T_{burst})$$

  $$B_{headroom}=B_{buffer}-B_{excess}$$

- 預設 `115200 baud`、每 byte `10 bits`、payload `512 B`、`10/s`、burst `20000 B/s`、`100 ms`、buffer `2048 B`，結果為 capacity `11520 B/s`、steady `5120 B/s`、利用率 `44.44%`、burst excess `848 B`、headroom `1200 B`。
- steady 超過 capacity 或 headroom 小於 0 時阻擋；burst 超過 capacity 但 buffer 足夠時顯示警告，建議 RTS/CTS、DMA/環形緩衝或升級介面。

### 假設與適用範圍

- `bits_byte` 代表 framing 後每一 byte 的總 bit 數，未再展開 parity、封包協定或模組內部 FIFO。
- 計算只估算 byte 流量，不保證 UART driver、RTOS 任務、DMA 或模組韌體能以同樣速率消費。
- SPI、SDIO、USB 只作介面取捨背景，不在此建模其時序。

### 常見錯誤模式

- 用 baud 當 byte/s，忘記每 byte 通常包含起始、資料與停止 bit。
- 只用 steady rate 判斷足夠，漏算模組回覆或 burst 期間的緩衝需求。
- UART 沒開硬體流控，或 ISR 直接解析長訊息，造成接收溢位與資料遺失。

### 可操作任務

- 調高 baud、payload、message rate 或 burst rate，觀察 utilization、burst excess 與 headroom。
- 先讓 burst 超過 UART 容量但 buffer 仍足夠，再把 buffer 降低到阻擋，說明兩種狀態差異。
- 為高吞吐情境選擇 RTS/CTS、DMA/環形緩衝或 SPI/SDIO/USB，並說明選擇依據。

## 模組 3：AT / URC 解析狀態

**模組鍵：** `at-engine`

### 學習目標

- 能區分命令回覆、URC、prompt 與透明資料，不把非同步事件誤當成目前命令的結果。
- 能依命令模式與資料模式維護狀態，理解 AT engine 為何需要佇列、逾時、重試與逐行解析。
- 能在 `data` 狀態缺少 transparent guard 時阻止不安全的資料路徑。

### 核心概念與狀態判斷

- `at-state`：`idle`、`wait`、`data`；`at-line`：`ok`、`error`、`urc`、`payload`、`prompt`。
- `pending command` 與 `URC handler` 各自是獨立條件；URC 可能插在任何命令往返中，必須先分流再交由 handler。
- OK/ERROR 只有 `wait + pending` 才能完成命令；否則是 unsolicited line 警告。
- prompt 只有 `wait + pending` 才能送 payload；payload 只有 `data` 才能進資料管道。
- `data` 狀態若缺 transparent guard 即阻擋；預設 `wait`、`urc`、pending yes、handler yes、guard yes，應分類為 URC、派送 handler，命令維持 wait。
- 教學狀態路徑：`IDLE → SENDING → WAIT_RESP`，逐行緩衝並比對 `OK`、`ERROR` 或特定前綴；不可在 ISR 裡 busy-wait 等回應。

### 假設與適用範圍

- 行分類依示例選項簡化，實際模組仍需以 AT command manual 定義的前綴、終結行與 escape 時序為準。
- transparent guard 是狀態防護概念，不是某一家模組的特定命令。
- 不在此深入解析 MQTT、TCP、TLS 內容或憑證信任。

### 常見錯誤模式

- 收到 URC 就結束目前 command，導致命令佇列與模組實際狀態不同步。
- 沒有 URC handler，卻把掉線、註冊變更或資料到達當成普通字串丟棄。
- 在命令仍 pending 時直接送 prompt payload，或忘記透明模式下的退出保護。
- 把整個 AT parser 放進 ISR，造成長時間阻塞與環形緩衝溢位。

### 可操作任務

- 切換 `at-line`，觀察同一個 pending 狀態下 OK、ERROR、URC、prompt 與 payload 的不同動作。
- 關閉 URC handler，確認結果被阻擋；切換為非 pending 後觀察 OK/ERROR 變成警告而非命令完成。
- 將狀態改成 `data` 並關閉 transparent guard，找出阻擋原因，再補回 guard。

## 模組 4：有上限的指數退避

**模組鍵：** `backoff`

### 學習目標

- 能用指數退避延後重連，避免網路或基地台不可用時形成重連風暴。
- 能計算某次嘗試的 nominal delay、jitter 範圍與截至目前的累積等待時間。
- 能辨識 retry exhaustion，將超過上限的責任交給 supervisor，而不是無限重試。

### 核心概念與公式

- 第 `n` 次 nominal delay：

  $$d_n=min(cap,base\times2^n)$$

- jitter 範圍：

  $$[d_n(1-j),d_n(1+j)]$$

  其中 `j` 由百分比換成小數。
- cumulative 是從 attempt `0` 到目前 attempt 的 nominal delay 加總，每一項都先套 cap。
- 預設 base `2 s`、attempt `4`、cap `60 s`、jitter `20%`、max retries `6`，結果為 nominal `32.0 s`、範圍 `25.6–38.4 s`、cumulative `62.0 s`。
- base/cap 必須大於 0；attempt/max retries 為非負整數；jitter 必須介於 `0–100%`；attempt 超過 max retries 時阻擋並轉 supervisor。

### 假設與適用範圍

- attempt 的編號從 0 開始；教學計算只處理等待時間，不估算入網、DNS、TLS 或 socket 建立時間。
- cap 是單次等待上限，不代表模組註冊一定能在 cap 內完成。
- jitter 只表示分散同時重連的隨機化範圍，不保證特定亂數分布。

### 常見錯誤模式

- 固定間隔或立即重試，讓已壅塞的網路與模組更難恢復。
- 指數成長沒有 cap，導致等待時間不可預期；或沒有 max retries，形成無限循環。
- 把每次 retry 的等待時間當成累積時間，漏算先前嘗試的延遲。

### 可操作任務

- 調整 base、attempt、cap 與 jitter，觀察 nominal、範圍與 cumulative。
- 將 attempt 調到超過 max retries，確認結果要求交給 supervisor。
- 比較有 cap 與無 cap 的概念結果，說明為何產品需要可觀測且有界的重連策略。

## 模組 5：分層會話重建

**模組鍵：** `session`

### 學習目標

- 能依固定順序重建註冊、IP、時間/DNS、socket、TLS 與應用會話，而不是一掉線就只重試最上層。
- 能找出第一個未通過的 gate，理解後續項目即使已勾選也不能抵銷前置缺口。
- 能依 network drop、DNS/time、TLS fail 與 app session 四種情境安排第一、第二診斷動作。

### 核心概念與判斷

- 固定 gate 順序：`registration → IP → time/DNS → socket → TLS → app session`。
- 六個檢查項對應 `session-registration`、`session-ip`、`session-time-dns`、`session-socket`、`session-tls`、`session-app`；預設前三項勾選，後三項未勾。
- 回報第一缺口、第二個建議檢查與下一步，不用總分抵銷前置失敗。
- 情境診斷：
  - `network-drop`：先查註冊/URC，再查 IP/socket。
  - `dns-time`：先確認時間源/DNS，再查 TLS。
  - `tls-fail`：先查時間/憑證設定，再看 socket/TLS log；此處只處理前置診斷，不展開憑證信任鏈。
  - `app-session`：先確認 transport，再恢復訂閱、QoS 與 sequence。

### 假設與適用範圍

- checkbox 代表已完成的診斷 gate，不代表真實網路一定可用。
- `time/DNS` 合併成裝置端前置條件；實作可由模組時間、NTP、RTC 或 DNS 設定共同提供，但不在此設計具體佈建方案。
- TCP、TLS、MQTT 的完整握手與安全語意留給既有筆記或安全量產知識群。

### 常見錯誤模式

- IP 或註冊尚未恢復就直接重建應用 session，造成無效重試。
- DNS 或裝置時間錯誤卻只重試 TLS，沒有先修前置條件。
- gate 只顯示勾選總數，沒有指出第一缺口，讓診斷順序失去意義。

### 可操作任務

- 依序補齊六個 gate，觀察 first、second、next 與 status 的變化。
- 切換四種 session case，比較同一組 gate 在不同故障情境下的第一診斷動作。
- 故意勾選後段但不勾前段，確認後段不能抵銷前段缺口。

## 模組 6：Payload 與資料預算

**模組鍵：** `data-budget`

### 學習目標

- 能把 payload、編碼比例、固定 overhead、訊息次數、delivery factor 與期間換算成 wire bytes。
- 能比較壓縮或緊湊編碼相對於 baseline 的節省率，並知道實際計費可能還包含額外協定與握手。
- 能以資料預算回頭檢查頻寬、電池、蜂巢式流量與上傳週期的取捨。

### 核心概念與公式

- 每訊息線上大小：

  $$B_{wire}=payload\times encoding\_ratio+overhead$$

- 每日與期間資料量：

  $$B_{day}=B_{wire}\times messages_{day}\times delivery\_factor$$

  $$B_{period}=B_{day}\times days$$

- baseline 使用 encoding ratio `1`；節省率：

  $$saving=1-\frac{B_{period}}{B_{baseline}}$$

- 預設 payload `100 B`、ratio `0.6`、overhead `40 B`、`24/day`、factor `1.1`、`30 days`，結果為 `100.0 B/message`、`2640 B/day`、`79200 B/30d`、baseline `110880 B`、saving `28.57%`。
- payload、overhead、messages、days 可為非負但 days 必須大於 0；ratio 必須 `0 < ratio ≤ 2`；factor 必須大於等於 1。

### 假設與適用範圍

- overhead 是教學用固定估計，實際 IP/TCP/TLS、MQTT/CoAP、重傳、握手與營運商計量方式需另外取得。
- delivery factor 用來表示重送或額外交付，不是可靠傳輸成功率的完整模型。
- 節省率只比較資料量，不直接等於電池壽命或總成本節省。

### 常見錯誤模式

- 只算 application payload，忽略編碼、標頭、重送與連線建立成本。
- 將 `ratio` 當成節省百分比，沒有再加上固定 overhead。
- 把 bytes 節省直接宣稱為能耗或月租等比例下降。

### 可操作任務

- 調整 payload、ratio 與 overhead，觀察每訊息、每日、期間資料量及 baseline saving。
- 增加 delivery factor，說明重送如何抵銷編碼節省。
- 將訊息週期從每日 24 次改成批次上傳，列出仍需實測的握手與計費項目。

## 模組 7：Keepalive、重連與 PSM

**模組鍵：** `keepalive`

### 學習目標

- 能計算持續會話的 keepalive 喚醒次數與 bytes，並與每次重連的資料成本比較。
- 能理解 frequent 與 rare reachability 對持續會話、PSM、eDRX 與批次上傳的不同影響。
- 知道網路 bytes 不等於能耗，低功耗判斷仍需把喚醒、發射、註冊與模組狀態納入實測。

### 核心概念與公式

- 喚醒次數：

  $$N_{wakes}=ceil\left(\frac{session\_hours\times3600}{keepalive\_seconds}\right)$$

- Keepalive bytes 與每日重連 bytes：

  $$B_{keepalive}=N_{wakes}\times roundtrip\_bytes$$

  $$B_{reconnect}=reports_{day}\times reconnect\_bytes$$

- 預設 keepalive `300 s`、session `24 h`、round trip `100 B`、reports `24/day`、reconnect `5000 B`，結果為 `288 wakes`、`28800 B` 與 `120000 B`；byte winner 為 keepalive。
- `frequent` 建議持續會話；`rare` 一律建議評估 PSM/eDRX/批次上傳，即使 reconnect bytes 較高，也要說明 bytes 與能耗不是同一個量。
- keepalive、session、reports 必須大於 0；bytes 欄位可為非負。

### 假設與適用範圍

- 喚醒次數以固定週期的上取整估算，不處理連線漂移、網路計時器、keepalive 逾時或封包重傳。
- PSM/eDRX 在此只作低功耗可達性的方向，不展開蜂巢式協定時序。
- reconnect bytes 是一次重連的教學估計，不代表特定營運商計費單位。

### 常見錯誤模式

- 以 keepalive bytes 較少就宣稱一定較省電，忽略每次喚醒與射頻啟動成本。
- rare 裝置仍維持高頻 keepalive，讓睡眠策略失效。
- 只設定應用層 keepalive，沒有確認模組、網路與 broker 的 idle timeout 是否相容。

### 可操作任務

- 調整 keepalive、session、round-trip bytes 與 reconnect bytes，找出 winner 交叉點。
- 切換 `frequent` 與 `rare`，觀察即使 byte winner 不變，建議仍如何改成 PSM/eDRX 或批次上傳。
- 為一個電池裝置寫出「喚醒 → 傳輸 → 回睡」的狀態，列出還需要電流剖面量測的項目。

## 模組 8：Supervisor 與故障升級

**模組鍵：** `supervisor`

### 學習目標

- 能依無回應、掉註冊、socket drop、buffer overflow 四種故障安排第一個觀測與第二個復原動作。
- 能把 log、timeout、backoff、soft reset、hard reset、flow control 與 watchdog 組成有界的升級路徑。
- 能理解 soft reset 無效時才應升級到 hard reset 或 power cycle，並保留故障證據供後續診斷。

### 核心概念與判斷

- 七個檢查項：`supervisor-log`、`supervisor-timeout`、`supervisor-backoff`、`supervisor-soft-reset`、`supervisor-hard-reset`、`supervisor-flow-control`、`supervisor-watchdog`；預設前三項勾選。
- 必要 gate：
  - `no-response` 需 log、timeout、soft reset、hard reset、watchdog。
  - `deregister` 需 log、timeout、backoff。
  - `socket-drop` 需 log、timeout、backoff。
  - `buffer-overflow` 需 log、flow control。
- 缺一即阻擋，不用總分抵銷必要項缺口。
- 診斷順序：
  - no-response：先保存 AT log/最後命令，再 soft reset，必要時 hard reset/power cycle。
  - deregister：先看 URC、訊號與註冊原因，再做 capped backoff。
  - socket-drop：先區分 bearer、IP 與 socket，再重建上層會話。
  - buffer-overflow：先看 RTS/CTS 與環形緩衝高水位，再降低 burst 或升級介面。
- supervisor 是 host 的復原協調層；硬體 WDT 可避免整機卡死，但不能取代 log、狀態機與故障原因分類。

### 假設與適用範圍

- checkbox 代表設計文件或韌體已有該機制，不代表故障注入已證明有效。
- `hard reset` 可抽象為拉 RESET 或斷電源域再上電；具體腳位時序需依模組 manual。
- 不在此處理 secure boot、金鑰、簽章 OTA、量產測試或法規要求。

### 常見錯誤模式

- 沒有保存最後命令與 URC log，就直接 power cycle，失去定位線索。
- 所有故障都用相同重啟路徑，沒有區分註冊失敗、socket 失敗與 host buffer 溢位。
- retry 沒有上限，或 soft reset 與 hard reset 沒有明確升級條件。
- 只依賴 watchdog，卻沒有 timeout、流控與應用會話恢復策略。

### 可操作任務

- 逐一切換四種 supervisor case，觀察 first/second 診斷建議與 blocker。
- 補齊某 case 的必要 checkbox，確認狀態從 blocked 變成通過；再取消一項觀察缺口。
- 為 no-response 與 buffer-overflow 各寫出一條「保存證據 → 軟處置 → 升級條件」流程。
