06 · C++ 感知介面與驗證證據

為什麼只回傳一個 Pose 很危險？

一句話答案：六個看似合理的數字，若沒有座標系、擷取時間、有效狀態、品質與來源，就無法知道它描述哪裡、哪一刻、是否可信。成熟介面傳遞的是「估測加證據契約」，而不是裸矩陣。

最小前置： 感知—控制閉迴路；熟悉 C++ 型別、所有權與錯誤處理。這章利用你的軟體背景把前面物理與幾何落到介面。

輸入契約先於演算法

影像輸入至少要說清楚寬、高、像素型別、色彩／深度編碼、列步距、擷取時間、相機識別、標定版本與緩衝區生命週期。若一個 stage 把 BGR 當 RGB，程式仍能跑；若把接收時間當擷取時間，靜止測試仍可能通過；若非同步工作保留已釋放的 buffer，錯誤甚至只在負載高時出現。用強型別與不可變 metadata 讓錯誤更早暴露。

輸出要回答五個問題

一筆估測必須回答：估的是什麼；來源與目標座標系是哪兩個；對應哪個擷取時間；有效或拒用的理由；數值不確定性與品質證據為何。協方差（Covariance）可描述局部誤差尺度與方向關聯，但它不是「可信度百分比」，也不會自動涵蓋標定錯誤、模型選錯與對稱多解。

struct PoseEstimate {
  RigidTransform T_target_source; // 名稱明示方向
  FrameId target_frame, source_frame;
  CaptureTime captured_at;
  Matrix6d covariance;
  QualityMetrics quality;         // 內點數、殘差、覆蓋等
  CalibrationVersion calibration;
  EstimateStatus status;          // 有效、退化、過期、無對應……
};

可手算的小例子

相機在 12:00:00.000 擷取影像，管線 70 ms 後輸出物體位置；物體相對速度 0.5 m/s。若下游誤把輸出時間當擷取時間，對齊姿態時就可能有 0.5×0.070=0.035 m，即 35 mm 的系統性時空錯配。把演算法位置雜訊從 2 mm 改善到 1 mm，完全救不了這個 metadata 錯誤。

自由實驗：最小輸出契約

逐項拿掉時間、座標或不確定度，觀察下游失去的是哪一種判斷能力。全部選「有」也只代表介面足以開始驗證，不代表估測已正確。

管線的觀測點與可重播性

在擷取、前處理、特徵、匹配、幾何估測、座標轉換及輸出各 stage 記錄結構化證據。保存能重播的原始輸入、參數與版本，使相同資料能離線重現。線上指標看延遲分位數、拒用率、飽和像素、有效深度比例、內點空間覆蓋與殘差；不要只記平均 FPS 與「success=true」。日誌也要有容量與隱私策略，避免無限制保存影像。

驗證要分層

  • 資料層：用已知小陣列驗證通道、步距、型別與生命週期。
  • 幾何層：用合成點交叉驗算投影、反投影與變換方向。
  • 標定層：看保留資料的每區域殘差，不以訓練資料自證。
  • 估測層：按距離、角度、材質、遮擋與退化類型統計位置／方向誤差和失敗率。
  • 系統層：量曝光到命令與致動的延遲分布，注入過期、缺幀、錯標定及低品質資料，確認拒用路徑。

常見誤解與邊界

例外不是所有即時管線的唯一錯誤機制；關鍵是失敗必須顯式且不可被當成有效零值。單元測試通過不代表相機、機器人與時鐘整合正確；模擬資料也很難涵蓋反光、模糊與硬體時間抖動。反過來，只有實機端到端測試又難以定位根因。分層測試、可重播輸入與線上證據需要同時存在。本章給的是契約骨架，不是功能安全認證方案；真正接近人或設備的系統仍需獨立安全控制與風險分析。

完成證據：任取一筆錯誤抓取，你應能沿時間戳、影像 metadata、標定版本、匹配與殘差、變換鏈及控制拒用狀態重建因果。若只能看到最後 Pose，就還沒有可診斷的感知系統。

痛點：裸 Pose 讓錯誤跨模組後失去身分

假設感知模組輸出位置 (0.4,0.1,0.8)，下游無法知道單位是公尺還是毫米、相對相機還是基座、對應現在還是 120 ms 前。數字本身甚至可能全部「在合理範圍內」，因此型別檢查和一般例外都抓不到。直到手臂抓偏，團隊才在十個模組間猜根因。輸出契約的目的就是讓每個估測攜帶足以被拒用、重播與驗證的上下文。

可把估測比喻成 API response：只有 payload 沒有 schema、timestamp、status 與 version，呼叫端只能猜。比喻的限制是機器人資料還有物理單位、座標方向與連續時間；精確契約必須同時約束數值布局與物理語意。

從一筆影像到一筆估測，逐欄問問題

  • 影像是誰的：相機序號與串流名稱避免左右相機或模擬／實機來源混用。
  • 何時擷取：硬體擷取時間與時鐘域，不能只存進入函式的系統時間。
  • 怎麼解讀：尺寸、步距、型別、色彩／深度單位及無效值規則。
  • 用哪份模型：標定與參數版本，讓離線重播能重建當時條件。
  • 輸出在哪裡：來源 frame、目標 frame、變換方向與旋轉慣例。
  • 為何可用：狀態碼、品質量、協方差與拒用理由。

這些欄位不是越多越好；每一欄都應對應一個下游決策。例如 captured_at 用來對齊機器人狀態，status 用來禁止把無效零值送入控制，calibration 用來判斷跨版本資料是否能比較。

第二組手算：單位與座標錯誤如何放大

感知輸出相機座標位置 (0.20,0.05,0.60) m；相機相對基座在簡化情況只平移 (0.50,0,0.80) m、軸向平行，因此基座位置為 (0.70,0.05,1.40) m。若下游漏做外參，直接把 (0.20,0.05,0.60) 當基座座標，位置差為 (−0.50,0,−0.80) m，遠大於演算法幾毫米的隨機誤差。

若另一介面把毫米值 (200,50,600) 填入宣告為公尺的欄位，範圍檢查應立刻拒絕。強型別可把 Meter、Millimeter 與 frame ID 包裝起來，卻仍無法知道外參是否量錯；軟體防呆與物理驗證是兩層工作。

狀態碼要讓失敗不能偷偷變成零

「沒有偵測」不是 Pose 全零，因為原點可能是合法位置；「深度無效」也不是 Z=0，因為下游可能解讀成碰到相機。狀態至少要區分輸入格式錯、過期、無特徵、幾何退化、求解失敗、品質不足與有效。每種狀態再帶必要診斷量，但避免把任意文字字串當唯一機器可讀資訊。

一次事件例如：frame 1042 擷取於 10.000 s，11 ms 後完成前處理，匹配僅 3 點，低於所需 4 點，因此回傳 insufficient_correspondences，不產生可用 Pose。log 應能把 frame ID、階段時間與拒用原因串起來；下游則依策略保持或停止，而非重用上一筆並改成新時間戳。

如何把重播設計成可回答的實驗

  1. 保存原始輸入位元組與完整 metadata，而不是只存經 JPEG 壓縮的截圖。
  2. 保存參數、模型檔雜湊、標定版本、程式版本與隨機種子。
  3. 每個 stage 輸出穩定摘要，例如特徵數、匹配對索引與殘差統計。
  4. 離線重跑後先找第一個不一致 stage，不要只比較最後 Pose。
  5. 用最小化輸入保留失敗：裁掉無關幀，但不能裁掉會影響時間與狀態的上下文。

位元級一致不是所有平行浮點系統都容易保證；若允許數值容差，就要明確寫出每個量的容差與單位。重播可證明同一保存條件下的軟體因果，不能重建未記錄的光線、溫度與硬體撓曲。

想更深入：協方差為何不能只塞一個 confidence

位置估測可能在 x 方向標準差 1 mm、z 方向 30 mm，單一 0.9 分數無法表達方向差異。若 x、z 又一起變動，還需非對角線相關項。協方差的直覺與計算可先讀機器人數學基礎 第 12 章：機率一點點；矩陣與向量基礎見第 4 章：矩陣乘向量。

即使矩陣格式正確，也要註明分量順序、座標系與旋轉擾動定義。消費端可檢查矩陣對稱、對角線非負與數值有限，這些只證明基本結構沒有明顯壞掉，不代表不確定度已由真值資料校準。

管線分 stage 的目的不是多畫幾個方框

每個 stage 應有明確輸入、輸出、失敗狀態與量測指標。擷取輸出帶 metadata 的影像；前處理輸出仍要保留時間與來源；特徵階段增加特徵座標與品質；幾何階段才產生位姿與殘差。若所有處理塞進單一函式，最後 Pose 錯時無法知道第一個異常出在哪。

但拆太細也會增加複製、排程與版本成本。邊界應選在資料語意改變或需要獨立驗證處，而不是每個小函式都變服務。離線先用單程序重播通常最容易控制變因。

第三組手算：佇列如何讓資料越跑越舊

相機每 33.3 ms 產生一幀，演算法平均每幀需 40 ms。每幀約多積 6.7 ms；連續 30 幀後，若不丟幀或限流，排隊延遲可增加約 30×6.7≈201 ms。畫面仍可能以約 25 fps 持續輸出，但內容越來越舊。

對即時控制，常見策略不是無限排隊，而是限定佇列長度、取最新幀並顯式記錄丟棄。這會犧牲逐幀完整性換新鮮度；離線檢測可能選擇相反策略。介面需說清楚用途，不能只追求「零掉幀」。

資料版本不相容時，拒用比自動猜測安全

影像解析度由 1280×720 改成 640×360，若只是等比例縮小且沒有裁切，像素焦距與主點通常也要按比例縮放；若有裁切，主點平移規則又不同。下游若仍載入舊標定，投影結果會系統性偏差。每幀帶 calibration ID，可讓消費端檢查是否有對應版本。

模型檔、前處理與標籤定義也要成組版本化。只換神經網路權重但沿用舊信心門檻，可能讓拒用率與誤報率改變。版本能證明使用哪份資產，不能證明新版本更好；仍需回歸資料與實機驗證。

一筆成功輸出至少要能回答的數字

  • 端到端 age：現在減 captured_at，而非單一函式耗時。
  • 輸入品質：飽和比例、模糊指標、有效深度比例。
  • 幾何品質：候選數、內點數、覆蓋、RMSE 與最大殘差。
  • 估測結果：frame、單位、位姿、協方差與狀態。
  • 可追溯性：frame ID、相機 ID、標定、模型與程式版本。

這些欄位要能以共同 event ID 串聯。若 log 只有不同執行緒各自的文字時間，時鐘與格式一變就難重建因果。

測試金字塔放進一個具體錯誤

錯誤情境是「右相機 BGR 被當 RGB」。單元測試用 2×1 人工像素驗證通道；整合測試餵已保存雙目影像，確認特徵與視差未異常；系統測試在已知治具上量深度；故障注入則故意切換編碼，確認介面檢查直接拒絕。每層回答不同問題。

若只有實機抓取失敗，根因定位慢；若只有小陣列測試，又無法涵蓋相機驅動宣告錯誤。測試應從可精確預期的小資料一路連到真實場景，而不是二選一。

互動輸出怎麼轉成介面設計決策

依序拿掉時間、frame 與不確定度：沒有時間，下游不能對齊動態狀態；沒有 frame，不能合法合成座標；沒有品質，下游無法按風險拒用。把三者都勾回來，只代表最小語意較完整，還需狀態碼、版本與輸入品質。

紙筆總練習：設計一筆能拒絕錯用的輸出

情境：frame 812 在硬體時鐘 15.200 s 擷取，70 ms 後求得相機到物體位姿；匹配 42、內點 31、RMSE 1.4 px、內點集中右半；使用標定 v7。輸出不應只有六個 Pose 數字，而要帶 captured_at=15.200 s、camera frame、object frame、T 的方向、status、協方差、品質、calibration=v7 與 event=812。

下游在 15.320 s 收到，age=120 ms。若過期門檻 80 ms，即使求解成功也應回傳或轉換為 stale，不送入正常控制。內點集中右半可另標記 coverage 偏低；是否直接拒用依已驗證門檻，但證據不能丟。

重播時用 event 812 找原始位元組與 metadata，確認 v7 參數、隨機種子與中間匹配。若離線 RMSE 變 0.9 px，先找第一個不同 stage；若輸入雜湊相同而匹配不同，查非決定性、模型版本或未保存狀態。

最後用已知治具驗物理位置。位元重播一致只能證明軟體重現當時結果；frame、時間與數值契約完整只能防止解讀錯；兩者都不能替代真值準確度。這四層結論應分開寫在驗收報告。

一分鐘版本：成熟的感知輸出是「估測＋時間＋座標＋狀態＋不確定度＋來源版本」。管線要在每個語意邊界留下可重播證據，讓任一失敗能找到第一個異常 stage。型別與版本防接線錯，保留資料和實體治具驗證物理正確性，兩者缺一不可。
新手常問：介面與證據還有哪些最低要求？

success=true 不夠嗎？它沒有失敗類型、品質與時效；同一布林值無法讓下游區分過期、退化與沒有物體。

時間戳用 double 秒可以嗎？數值容器可以，但還要定義時鐘來源、紀元、精度與是否單調；不同機器的秒不能直接相減。

frame 名稱用字串有何風險？拼字可在執行時才失敗，且無法保證變換存在。應有受控 ID 與可查版本的座標圖。

協方差全零代表完美嗎？通常更可能代表未計算或錯誤預設。未知不確定度要有顯式狀態，不能偽裝成確定。

把所有影像永遠保存最可重播嗎？會遇到容量、隱私與安全問題。應有取樣、事件觸發、保留期限、存取控制與去識別策略。

log 越多越好嗎？過量文字會擾動即時性且難查。優先結構化關鍵欄位、事件關聯與分層摘要，錯誤事件再附原始資料。

浮點結果每次差最後幾位算失敗嗎？依契約。需要位元重現就控制執行順序；允許容差則按物理單位與風險定義，不用無來源 epsilon。

單元測試能測時間嗎？可用虛擬時鐘測過期與排序邏輯；真實驅動、排程抖動仍需整合與硬體量測。

如何避免舊標定被誤用？輸入與估測都帶版本，啟動與每筆資料檢查相容性，部署系統保留資產組合與回滾紀錄。

完成標準：給任一錯誤 Pose，能以 event ID 找回原始幀、時間、frame、參數版本、中間品質、拒用決策與當時機器人狀態。

把不確定度的量綱寫進介面審查

六自由度位姿常把三個平移與三個小角度擾動放進同一個 6×6 協方差。平移對角項的單位是 m2，旋轉對角項是 rad2，交叉項則可能是 m·rad；矩陣裡的數字不能脫離分量順序與擾動定義解讀。例：若 x 變異為 4×10−6 m2，標準差是 √(4×10−6)=0.002 m=2 mm；若 yaw 變異為 9×10−4 rad2，標準差是 0.03 rad，約 1.72°。把兩者都顯示成「0.00」會同時丟失單位與風險。

這種局部協方差還需要說明旋轉參數化、左擾動或右擾動，以及它表達在哪個座標系。否則兩個模組即使都傳 Matrix6d，也可能在數學上解讀不同。型別系統能防止一部分接線錯誤，不能替代這份語意契約。

一筆失敗如何沿管線重播

  1. 輸入操作：以原始影像、擷取時間與標定版本重播同一幀。
  2. 中間狀態：逐 stage 比對影像摘要、特徵數、匹配雜湊、內點集合與座標變換版本。
  3. 輸出結果：確認 Pose、協方差、狀態碼和線上版本是否一致。
  4. 外部證據：對齊當時機器人狀態、命令與安全控制 log，定位錯誤是在感知內部還是使用時機。

位元完全相同的輸入仍無法重現時，常見原因是未保存參數、非決定性平行歸約、隨機種子或外部狀態。可重播能證明軟體在保存條件下如何產生結果；它不能重建未記錄的照明、溫度或機械撓曲。因此線上證據與受控實機實驗仍不可少。
