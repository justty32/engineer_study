13 · 把整條鏈收回同一張圖

從 C++ 原始碼到執行證據

逆向工程不是看到組合語言就猜原始碼，而是先判斷你手上的證據位於哪一層、哪些轉換已發生、哪些資訊不可逆地消失。

先看痛點：錯誤訊息所在位置不一定是根因所在層

程序在位址 0x7ABC1234 崩潰，只能先證明 CPU 在那裡遇到例外；它不直接證明那一行原始碼寫錯，也不告訴你物件何時被破壞。相反地，連結器說未定義符號時，去單步執行根本沒有成品可跑。有效調查要先分類「目前最後一個成功產物」與「第一個失敗證據」，再選能回答該層問題的工具。

先選失敗時機

切換症狀後，留意建議證據如何從來源文字一路移到執行狀態。工具越靠後，通常越接近實際行為，但高階名稱與型別資訊也可能越少。

證據矩陣

原始碼／編譯層

巨集展開、編譯選項、診斷、中介表示、產生的組合語言。它們適合回答編譯器看見什麼與做了哪些轉換。

目的檔／連結層

區段、符號、重定位、函式庫選取與連結映射。它們回答名稱如何綁定與位址如何完成。

檔案／載入層

映像標頭、目標架構、相依函式庫、搜尋路徑與虛擬映射。它們回答磁碟成品能否成為本機程序。

執行層

指令位址、暫存器、呼叫堆疊、頁面權限、例外、系統呼叫與日誌。它們回答某次執行實際走了什麼路。

案例一：未定義符號的最短證據鏈

  1. 編譯兩個翻譯單元，確認呼叫端目的檔已產生，排除前端語法或型別失敗。
  2. 從連結診斷取得「真正未解析的修飾符號」，不要只靠反修飾後的好讀名稱。
  3. 檢查呼叫端符號表，確認它確實有未定義引用；再檢查預期供應者是否輸出完全相同的定義。
  4. 若定義存在，核對該目的檔或函式庫是否真的進入這次連結、抽取順序與可見性是否正確。
  5. 修正後保存連結映射或最終符號表，證明引用已綁到哪個輸入。程序尚未執行，因此執行期 log 不能替代這條鏈。

案例二：把 ASLR 下的崩潰位址對回檔案

假設崩潰 PC=0x7F201234，模組在該次程序的載入基底為 0x7F200000，則模組相對位移為 0x1234。接著用「同一份未剝除或具配對除錯資訊的二進位檔」查 0x1234 附近的函式、指令與來源行。若拿另一個建置版本查，即使函式名稱相同，布局也可能已改變。

在該指令前後檢查暫存器與記憶體：若指令從 [RDI+8] 載入，而 RDI 是 0，故障有效位址接近 0x8，可支持空指標加欄位位移的推論；但還要沿呼叫鏈或資料寫入點追問 RDI 為何成為 0。崩潰點是症狀的精確位置，不必然是最早的錯誤。

案例三：來源行與機器指令不再一對一

一行 return x*2+1; 可能折成一條位址計算類指令；整個小函式可能被內聯到多個呼叫點；未使用結果可能完全消失。除錯資訊提供的是對照關係，不是原始碼逐行錄影。單步時跳行、變數顯示「已最佳化」或多條來源行共用位址，都可能是合法最佳化結果。需要確認語意時，同時查看最佳化選項、反組譯、行號表與實際狀態。

一份可重複使用的調查順序

  1. 固定成品：記錄檔案雜湊、架構、建置選項與除錯資訊是否匹配，避免證據來自不同版本。
  2. 定位層級：確認最後成功的是預處理、目的檔、最終映像、程序建立還是進入 main。
  3. 收集原始證據：保留完整診斷、位址、暫存器、映射與相依清單，再做解讀；不要只截取最後一句錯誤。
  4. 建立最短因果鏈：把操作、狀態變化、結果與觀察工具逐項對上，標示哪些是直接觀察、哪些是推論。
  5. 用第二種證據交叉檢查：例如符號表配重定位、映射基底配反組譯、暫存器值配記憶體位元組。
  6. 寫下工具邊界：未載入符號時的函式名、最佳化後的變數值與取樣式追蹤都可能不完整。
想更深入：何謂「能證明」與「不能證明」？

反組譯中存在某條指令，能證明指定二進位位元組可被該工具按目標 ISA 解碼成那條指令；它不能證明控制流一定執行它。一次除錯器停點能證明該次執行到達並暴露當下狀態；它不能證明所有輸入都走同一路。日誌能證明程式曾嘗試記錄某事件，但緩衝、崩潰與多執行緒排序會影響完整性。把結論限制在證據真正涵蓋的範圍，逆向才不會從「可能」滑成「一定」。

你現在能獨立完成的口述檢核

  • 從 MOSFET 受控開關說到 NAND、組合邏輯、正反器、暫存器與資料路徑，每一層都指出抽象省略了什麼。
  • 拿一條載入、算術、分支與呼叫指令，分別說明暫存器、記憶體、旗標或 PC 如何改變。
  • 比較 x86-64、AArch64 與 RISC-V 的寬度視圖、記憶體運算元、旗標與返回位置，不把 ABI 當 ISA。
  • 從 C++ 翻譯單元追到目的檔、符號、重定位、最終映像、載入映射與 main 前初始化。
  • 遇到錯誤時說出工具能直接證明什麼、仍需哪一項交叉證據，而不是只報一個猜測。
