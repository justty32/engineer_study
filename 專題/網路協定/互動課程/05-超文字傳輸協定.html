05・應用訊息

超文字傳輸協定：程式如何說「我要這個資源」？

超文字傳輸協定（Hypertext Transfer Protocol, HTTP）定義客戶端請求與伺服器回應的語意與格式。方法表達動作，目標指出資源，標頭攜帶中介資訊，狀態碼描述處理結果。

這章假設已懂：名稱先解析成位址，再由傳輸層把位元組送到服務埠。

把 HTTP 看成遠端訊息，不是函式呼叫

方法、路徑、標頭與本文很像呼叫介面的動作、參數與資料，狀態碼則像結構化結果；這能幫助程式設計者抓住語意。真實 HTTP 是跨程序、跨網路的訊息協定，可能經過代理、快取與閘道，逾時或重送也讓它不像單機函式那樣具有天然的「只執行一次」語意。

實驗怎麼玩

選 GET 並改變路徑，觀察資源目標如何進入示意請求；改成 HEAD，注意它要求與 GET 相同的回應標頭語意但不傳回回應本文；改成 POST，想像本文承載要處理的表示。再逐一切換 200、301、404、500：狀態碼是伺服器回覆的應用結果，不是由方法直接算出，本工具刻意讓兩者自由組合。

自由實驗：組一組請求與回應

從 URL 拆出真正參與者

以一組教學欄位為例：https 是方案，決定使用受 TLS 保護的 HTTP；example.test 是主機名稱，交給 DNS；8443 是明示埠，交給傳輸層；/articles/42 是路徑，view=full 是查詢。這些欄位合在一起才構成 URL；伺服器收到後，依自己的路由規則把目標映射到程式處理器。URL 本身不是磁碟檔案路徑，也不保證後端如何實作。

一個交換的因果

客戶端已有傳輸連線送方法、目標、標頭與可選本文伺服器路由到資源處理器產生狀態、標頭與可選本文客戶端依語意採取後續動作

狀態碼第一位表示大類：1xx 資訊、2xx 成功、3xx 需要後續動作、4xx 請求端相關問題、5xx 伺服器處理失敗。這只是分類，不代表所有 4xx 都能靠「重送相同請求」解決。

例如客戶端送出 GET /articles/42，伺服器回 301 並附新位置，狀態變化是客戶端取得「應改向何處」的資訊；是否自動跟隨由客戶端政策決定。若回 404，證據顯示 HTTP 已到達能產生回應的元件，但不能由此判定是使用者打錯、路由規則不符、權限刻意隱藏資源，或後端資料真的不存在。

版本改變承載，不抹掉語意

HTTP 第一版點一通常以文字起始行與標頭示範；HTTP 第二版（HTTP/2）把同一連線上的多個資料流二進位分框並壓縮標頭；HTTP 第三版（HTTP/3）改以快速使用者資料包網際網路連線（QUIC，原為 Quick UDP Internet Connections 的名稱，現為協定專名）承載多資料流。方法、狀態碼與資源語意仍屬 HTTP。

狀態與證據

瀏覽器開發工具或應用追蹤能看到方法、網址、標頭、狀態與時間；傳輸封包只會看到承載位元組，若有加密甚至看不到 HTTP 明文。伺服器存取紀錄通常可證明請求到達應用入口，但不一定證明後端交易完成，仍要串接業務紀錄。

診斷時把時間拆開：DNS、建立連線、TLS、等待第一個回應位元組與下載本文分別代表不同階段。開發工具的總耗時能指出「使用者等了多久」，但若工具未提供分段計時，不能只憑總數字把責任歸給網路或伺服器。

不要混淆

  • HTTP 是應用協定；傳輸控制協定是傳輸服務；兩者不互相取代。
  • 成功建立連線不代表請求成功；得到 404 反而證明應用層已有回應。
  • 無狀態表示每個請求的協定語意可獨立理解，不表示服務不能用瀏覽器小型狀態資料（cookie）、權杖或資料庫保存會話。
