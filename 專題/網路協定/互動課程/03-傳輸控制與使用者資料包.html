03・端對端傳輸

傳輸控制協定與使用者資料包協定：應用需要哪些保證？

使用者資料包協定（User Datagram Protocol, UDP）保留每個資料包邊界，只加入來源埠、目的埠、長度與檢查和，標頭共 8 位元組，不替應用建立可靠性。傳輸控制協定（Transmission Control Protocol, TCP）建立連線狀態，以序號、確認、重傳、流量控制與擁塞控制提供有序可靠的位元組流。

這章假設已懂：網際網路協定（Internet Protocol, IP）只做盡力逐跳轉送。

先問應用能承受哪種失敗

選 TCP 或 UDP 不是選「高級版」與「簡單版」，而是在決定可靠性、時效性與訊息邊界由哪一層負責。檔案少一段通常不可接受，交給 TCP 重排與重傳很自然；即時語音的舊片段即使補到也可能已無播放價值，應用可能寧可丟掉。真實選擇還會考慮延遲、網路環境、協定生態與安全機制。

實驗怎麼玩

先保持「完整且有序」，分別選 TCP、UDP，再提高示意遺失率，觀察誰負責恢復。接著取消完整有序需求，看即時性優先的語意如何改變判斷。滑桿不是在預測真實吞吐量；每次遺失是否發生、TCP 何時重傳及延遲多大，還取決於往返時間、計時器、確認與擁塞狀態。

自由實驗：改變保證與遺失

用機率建立直覺，但別當成保證

若為了教學暫時假設每個資料包獨立、遺失機率固定為 p，一次送出 n 個資料包且全部首次成功的機率是 (1 − p)n，為無單位比值。以 p = 0.05、n = 20 為例，0.9520 ≈ 0.358，也就是只有約 35.8% 的批次首次完全到齊。這說明少量單包遺失率累積後不可忽略。

真實網路的遺失常成串且彼此相關，TCP 也會重傳，所以這個式子不能預測檔案成功率或完成時間；它只幫你理解「應用若要求完整，誰來處理缺口」的重要性。

埠是作業系統內的分流標籤

埠（port）讓同一個 IP 位址上的多個程式端點並存。來源與目的 IP 位址、來源與目的埠，加上傳輸協定種類，通常共同辨認一條資料流。埠不是實體插孔，也不是遠端程式的永久身分。

TCP 連線如何改變狀態

客戶端送同步序號旗標伺服器回同步與確認客戶端確認雙方進入已建立以序號追蹤位元組

同步序號（synchronize sequence numbers, SYN）與確認（acknowledgment, ACK）旗標組成常說的三次握手。序號說明資料位元組的位置；確認表示下一個期待的位置。遺失造成確認缺口或計時器到期時才可能重傳。接收窗避免送端淹沒接收端；擁塞控制則避免對網路注入過多流量，兩者不是同一件事。下方74 位元組 TCP SYN 訊框展示第一步實際如何排成位元組。

例如接收端已連續收到序號涵蓋位元組 1000～1499，就會以確認號 1500 表示「下一個期待 1500」，不是表示只收到編號 1500 的封包。若 1500～1999 遺失而後面的資料先到，接收端仍會暴露缺口，送端可依重複確認或重傳計時器補送。實際序號會回繞，確認與選擇性確認行為也受協商與實作影響。

74 位元組 TCP SYN 訊框逐欄位解剖

這是一個完整、無應用負載的乙太網路 II 訊框：14 B 乙太網路標頭＋20 B IPv4 標頭＋40 B TCP 標頭。擷取資料不含前導碼、訊框間隔與訊框檢查序列（Frame Check Sequence, FCS），所以長度是 74 B 而不是整段實體線路開銷。MAC 與 IP 都使用文件範例值，不代表真實端點。

操作：滑過、點選或用 Tab 聚焦十六進位位元組與欄位列，兩邊會同步高亮；Enter 或空白鍵可鎖定，Esc 取消。以層級篩選時，十六進位傾印仍保留完整 74 B，非該層的位元組會淡出。

層欄位名位移長度原始值解讀值說明

回看欄位為何存在：00 封裝與長度、01 本地下一跳與 MAC、02 IPv4 與路由、03 TCP 握手與序號。

TCP 如何關閉與拒絕連線

正常關閉時，一端送結束（finish, FIN）並收到確認，另一端也以 FIN 告知已送完，因此常被稱為「四次揮手」。主動關閉的一端通常進入 TIME_WAIT，保留一段時間以處理舊區段與重送的最後確認。重設（reset, RST）則是立即中止或拒絕狀態；例如目的主機可達但沒有程式監聽該 TCP 埠時，可回 RST。這與 SYN 無回應直到逾時不同：前者是明確拒絕證據，後者只表示期限內沒收到預期回覆。TCP 最大區段大小（Maximum Segment Size, MSS）會在握手時告知對方自己願意接收的 TCP 負載上限。

邊界與取捨

UDP 的「低負擔」不等於永遠低延遲：應用若自行補上複雜可靠性，成本仍存在。TCP 的「可靠」只保證交給對端傳輸層的位元組流，不保證應用成功寫入資料庫。即時語音可允許舊片段遺失而偏好新鮮資料；檔案通常需要完整有序。選擇源於應用語意，不是協定排名。

證據

封包可看到來源／目的埠、TCP 序號、確認、旗標、窗與重傳跡象；作業系統可看到監聽、連線中、已建立、等待關閉等狀態；應用紀錄才能說明已收到的位元組是否通過業務驗證。

在本機取得證據

ss -tn
ss -ltn

預期輸出樣貌：已建立連線可呈現 ESTAB 0 0 192.0.2.10:49152 198.51.100.20:443，監聽端點可呈現 LISTEN 0 4096 0.0.0.0:8080 0.0.0.0:*；文件位址、埠與佇列數字只示意欄位。前者對照兩端 IP、埠與 TCP 狀態，後者可區分「本機有程式監聽」和「已有端對端連線」；兩者都不證明應用交易成功。

不要混淆

  • TCP 的「連線」是兩端維護的協定狀態，不是一條被永久占用的實體線路。
  • 接收窗（receiver window）處理接收端容量；擁塞窗（congestion window）估計網路承受能力，限制來源不同。
  • UDP 保留資料包邊界；TCP 只提供位元組順序，應用必須自訂長度欄位或分隔規則。
  • 看到重傳可支持某段資料未及時獲確認，卻不能單靠一個「重傳」標記確定是網路遺失；延遲、重新排序與擷取位置也會影響判讀。
