# 工業工程整合專題（IE Capstone: Systems Integration & Senior Design）

> 名詞對照見 [中英名詞對照表 → 工業工程整合專題](../中英名詞對照表.md#工業工程整合專題)。

## 0. 本科定位

這是工業工程大學教育的**最後一哩路**——前面每一科都是工具箱裡的一把工具：統計教你把雜訊從訊號中分離出來、作業研究教你建立決策的數學模型、模擬教你重現複雜系統的行為、品質工程教你辨識變異的源頭、人因工程教你讓人與系統協調、工程經濟教你衡量方案的金錢價值——但真正在現場面對一個問題時，你**該從工具箱拿出哪一把工具？用什麼順序？這些工具之間如何串接成一個有說服力的分析？**

這就是整合專題的核心訓練：**系統整合思維（systems integration thinking）**。你不是在一個封閉的練習題裡操作單一工具，而是面對一個真實（或擬真）的組織問題——問題陳述模糊、資料不完整、利害關係人意見分歧、預算與時間有限——你必須自己定義問題邊界、設計研究路線、選擇模型工具、解釋分析結果、並將結論轉化為管理層聽得懂的決策建議。

典型的大學整合專題（senior design / capstone）採取**專案實作**形式：學生（通常以團隊）與業界或校園營運單位合作，在一個學期或一學年內完成一項完整的改善或設計專案。產出不是「計算正確的考卷」，而是**一份經得起各方質疑的專案報告**，以及向利害關係人（教授、業主、同儕）的口頭簡報。這也是 ABET 工程教育認證中要求學生展現「在真實限制下（經濟、環境、社會、安全、倫理），整合運用所學以設計系統或組件」能力的那門課。

工業工程的整合專題，與其他工程科系（機械、電機、化工等）的 senior design 有什麼本質的不同？機械系做出一台機器、電機系做出一套電路或系統——產出是**硬體**。IE 的整合專題產出是一套**系統設計或改善方案**——它可能包含 layout 重設計、排程規則重寫、庫存政策調整、品檢流程改造、人員編制最適化，這些方案背後是數據分析、模型推導與模擬驗證，但最終影響的是組織的運作方式。所以 IE 整合專題的難點不在於「東西做不出來」，而在於**方案是否真的解決對的問題、數據是否支持結論、改變是否能在組織內落地**。

> **核心心法**：整合專題不是把所有學過的工具都塞進同一個報告裡——那是工具展演，不是問題解決。正確的態度是：讓問題本身決定需要什麼工具。先用系統思維釐清問題的邊界與因果結構，再從工具箱中選出最精簡、最適切的方法組合。如果一個問題用簡單的柏拉圖分析加流程圖就能解釋清楚，那就不需要造一個離散事件模擬模型。

## 1. IE 專案方法論——從問題到方案的六階段

工程改善不是「看到問題就直接跳到解法」——那樣做的風險是花了大量資源改善一個不是瓶頸的環節、或解決了一個表面症狀卻讓真正的病因在其他地方復發。IE 有一套結構化的方法論引導專案從混沌走向清晰。以下六階段是整合專題的骨架——每一個成功的 IE 專案，無論是 DMAIC 還是精實改善周（kaizen event），底層都遵循這套邏輯。

### 1.1 問題定義（Problem Definition）

這是**專案最重要的階段**——也是最容易被跳過的階段。決定「我們到底在解決什麼問題」聽起來像廢話，但實務上大部分的失敗專案追溯根因，都出在問題陳述模糊或方向錯誤。

一個良好的問題定義應包含：
- **客戶是誰（who is the customer）**：最終受益者是誰？產線經理？物流課長？終端消費者？不同客戶對「好」的定義不同——產線經理在乎產能達成率，物流課長在乎出貨準時率，消費者在乎到貨速度。你無法同時最大化所有維度，必須在定義階段就釐清**誰的痛點是優先**。
- **現況與目標的差距（gap）**：用可量化的指標描述「現在是多少」vs「想變成多少」。不是「我們想改善效率」——這是空洞的陳述；而是「產線 A 的整體設備效率 OEE 目前為 62%，目標提升至 75%」——這樣你才知道何時算成功。
- **邊界與限制（scope and constraints）**：哪些在範圍內？哪些不在？預算上限、時間期限、不可更動的既有設施、法規與安全要求。**寫下範圍的「負面清單」**（明確說哪些不碰）和正面清單一樣重要——可以避免利害關係人之後的期望落差（「我以為你們會順便處理倉庫那塊」）。
- **誰是決策者與利害關係人（stakeholders）**：你的方案最終要說服誰？他們在乎什麼？他們有多少技術背景？這些會直接影響你的分析深度與呈現方式。

一個很實用的技巧是**問題陳述模板**：「[組織/系統] 的 [指標 A] 目前為 [現況值]，目標為 [目標值]，限制為 [時間/預算/不可改動的部分]，成功將使 [客戶] 獲得 [效益]。」強迫自己填完這個模板，通常就能發現問題定義中的模糊地帶。

### 1.2 資料收集與分析（Data Collection & Analysis）

定義完問題後，你手上可能有一堆資訊——現場人員的抱怨、管理層的直覺、ERP 匯出的 Excel 報表、歷史客訴紀錄。這個階段的任務是把這些原始素材轉化為**可分析、可建模的結構化資料**。

**前置工作：資料盤點**

先問自己三個問題：
1. 什麼資料已經存在？（ERP、MES、倉儲管理系統的日常紀錄、客服日誌、品質檢驗報告）
2. 什麼資料需要額外收集？（量測耗時、或需要現場觀察才能取得的定性資訊——如作業員的走動路徑、機台暫停的頻率與原因）
3. 既有資料的品質如何？（缺值比例、錄入錯誤、不同系統間的定義不一致——例如「出貨完成」在 ERP 和在倉儲系統的定義可能不同）

**量測系統分析（measurement system analysis, MSA）**：如果你打算用數據做判決，就必須先確定量測本身是否可靠。兩個基本概念：(1) **準確度（accuracy）**——量測值與真值的偏離程度；(2) **精密度（precision）**——重複量測之間的一致性。一個不精確的量測系統（如每天手動抄錶、不同班別抄錶的位置不同）產生的變異不是你製程的變異，而是量測的雜訊——你用這種資料做的任何統計推論都不可靠。在 IE 專案中，量測系統通常不是精密儀器，而是**人工記錄**（作業時間、計數、分類）——記錄者之間的差異（inter-rater variability）往往是最大的誤差來源。

**探索性資料分析（exploratory data analysis, EDA）**：在鑽進複雜建模之前，先用最簡單的工具認識資料：(1) **摘要統計**——平均數、標準差、中位數、四分位距；(2) **視覺化**——直方圖看分布形狀、時間序列圖看趨勢與週期、散佈圖看兩變數的相關；(3) **分群比較**——把資料按班別、機台、產品別、時段切開來看，差異往往直接指向根因。EDA 的目標不是精確推論，而是**發展直覺與假說**——「咦，為什麼週三下午的報廢率特別高？對應到什麼現場事件？」

### 1.3 建模（Modeling）

資料探索完畢、對問題的結構有了初步理解，接下來是選擇並建立一套**模型**——模型是「簡化版的現實」，目的是讓你能夠在有限的變因下分析因果關係、做預測或最佳化，而不必在真實系統上反覆實驗（那可能極其昂貴或危險）。

IE 常用的模型大類與選擇邏輯：

**解析模型（analytical models）**——當系統的行為可以用數學公式封閉地表達時使用：
- **線性規劃／整數規劃（LP/IP）**：適用於資源分配、排程、生產組合、運輸路線等「在限制條件下最大化／最小化某個線性目標」的場景。優點是求解極快、且提供影子價格（shadow price）這類豐富的敏感度資訊；缺點是必須假設線性關係，非線性或隨機因素難以嵌入。
- **排隊模型（queueing models）**：適用於服務系統（客服中心、檢驗站、銀行櫃檯）的等待時間、隊列長度、利用率分析。用 Kendall 記號 M/M/c 等基本模型可以手算穩態績效，前提是到達與服務時間符合標準分布。
- **庫存模型（inventory models）**：EOQ、報童模型（newsvendor）、(s, S) 政策等——適用於「訂多少、何時訂」這類存貨決策。

**模擬模型（simulation models）**——當系統太複雜、太多隨機性與交互作用，解析模型無能為力時：
- **離散事件模擬（discrete event simulation, DES）**：IE 最核心的模擬工具。系統狀態僅在「事件」發生瞬間改變——一個工件抵達機台、一個作業員完成作業、一台 AGV 卸貨。適合製造系統、物流系統、醫院流程等。軟體如 Arena、Simio、FlexSim。
- **代理人基模擬（agent-based simulation, ABM）**：當系統中的個體有異質行為規則、彼此互動產生湧現現象（emergence）時使用——例如多台 AMR 倉儲機器人彼此避碰的路徑選擇、或消費者個別選擇行為對市場的影響。
- **系統動力學（system dynamics）**：用存量（stock）與流量（flow）的微分方程描述系統的巨觀行為——適合供應鏈長鞭效應、市場成長與衰退等「回饋迴路驅動」的長期動態。存量代表累積（庫存、產能、員工人數），流量代表變化率（生產速率、招聘速率）。

**統計模型**——當你的目標是建立輸入與輸出之間的因果或相關關係：
- **迴歸分析**：$y = \beta_0 + \beta_1 x_1 + \dots + \beta_k x_k + \epsilon$，用來量化「某個因子改變一單位，產出改變多少」。
- **實驗設計（DOE）**：主動操控因子水準來觀察對輸出的影響，適合製程參數最佳化。
- **時間數列模型**：用歷史資料預測未來（需求預測、設備故障時間預測）。

**模型選擇的決策邏輯（對 IE 整合專題特別重要）**：

```
問題的本質是什麼？
├── 資源分配、成本最小化、排程組合
│   └── 關係是否線性、變數量合理？
│       ├── 是 → LP/IP（解析）
│       └── 否、或太複雜 → 啟發式演算法（heuristics）或模擬
├── 系統隨時間演進，有隨機到達與服務
│   └── 交互作用是否複雜？
│       ├── 否 → 排隊理論（解析）
│       └── 是 → 離散事件模擬
├── 想建立因子與產出的因果關係
│   └── 可以操控因子嗎？
│       ├── 是 → DOE
│       └── 否 → 迴歸（觀察性資料）
└── 系統層級的動態行為（回饋、延遲、非線性）
    └── 系統動力學模擬
```

**模型驗證（validation）**——模型建好之後，必須回答一個關鍵問題：這個模型在多大程度上反映了真實系統？驗證通常分兩層：(1) **表面效度（face validity）**——拿給現場專家看模型的邏輯與輸出，他們直覺上覺得合理嗎？(2) **統計驗證**——比對模型的輸出與真實系統的歷史數據（例如模擬出來的產能 vs 過去六個月的實際產能），用 t 檢定或信賴區間檢查差異是否在可接受範圍內。一個沒有經過驗證的模型產出的「最佳解」，跟擲骰子沒有本質區別。

### 1.4 分析與最佳化（Analysis & Optimization）

模型驗證完成後，開始用它來回答原始問題。這個階段的關鍵紀律是：**不要只跑一個情境就下結論**。

**實驗設計精神在分析中的應用**：即使你不做正式的 DOE，也應該有系統地變化關鍵輸入參數、觀察輸出如何變化。(1) **基線情境（baseline scenario）**——先用模型重現現況（current state），確認模型忠實反映現實；(2) **改善情境（what-if scenarios）**——逐一測試不同的改善方案；(3) **假設參數變動**——你的資料一定有不確定性（例如機台平均故障間隔真的就是那個數字嗎？實際可能正負 20%），對關鍵參數做變動再跑模擬，觀察結論是否翻轉。

**敏感度分析（sensitivity analysis）**是這個階段最重要的工具。它的核心問題是：**哪個參數對結果的影響最大？** 回答這個問題的價值在於：(1) 告訴你改善資源該花在哪裡——如果某一站的加工時間變異對整體產能的影響遠大於其他任何因子，那改善這一站就是最高投資報酬率的選項；(2) 檢驗結論的穩健性——如果你的最佳方案只在某個假設參數落在一個狹窄範圍內才成立，那這個方案就不穩健，需要重新評估。

敏感度分析有幾種做法：
- **一次一個因子（one-factor-at-a-time, OFAT）**：固定其他因子，逐一變動單一因子觀察輸出變化。簡單快速，但無法捕捉因子間的交互作用（兩個因子各自對輸出影響不大，但同時變動時輸出劇變）。
- **龍捲風圖（tornado diagram）**：把各因子的影響幅度用水平長條圖排序，一眼看出哪些是「驅動因子」。
- **蒙地卡羅模擬**：對所有不確定參數同時取樣（從它們各自的機率分布中抽值），重複執行模型數千次，得出輸出結果的機率分布——這比單點估計更能反映風險全貌。

**最佳化的陷阱**：模型跑出的「數學最佳解」不等於「實務最佳方案」。例如 LP 模型可能建議把某產品的產量設為 238.7 件——但實際生產是整批（batch）的，你只能做 200 或 250 件；或是建議在兩個工廠之間精細調度——但這麼做會讓排程頻繁變動、現場人員無所適從（頻繁換線本身就有成本）。好的 IE 分析師永遠在數學解與實務可操作性之間尋找**滿足解（satisficing solution）**——夠好、夠穩健、實務上能執行的方案，而非紙上完美的理論解。

### 1.5 建議（Recommendation）

分析跑完了，但你還沒有「完成」——**把技術分析翻譯成決策語言，才是 IE 工程師區隔於純分析師的關鍵能力**。

一個完整的建議方案應包含以下要素：
- **方案摘要**：用一段話講清楚你建議做什麼。不要用術語堆砌——目標是讓一個不具 IE 背景的高階主管讀完這段就知道你的結論。如果你不能用一段話講清楚，表示你自己還沒有想清楚。
- **選項比較**：不要只提出一個方案說「這是最好的」，而是列出 2–3 個可行方案，每個方案的優劣（成本、時間、風險、對日常營運的干擾程度），以及為何你最推薦其中一個。這做法有兩個好處：(1) 展現你做了全面考量而非 tunnel vision；(2) 給決策者選擇權——決策者可能需要考慮你無法掌握的資訊（例如組織近期有人事異動），有多個選項讓他們能做出知情決策。
- **成本效益分析（cost-benefit analysis）**：任何改善方案都有成本——顯性成本（設備採購、顧問費、軟體授權、加班費）和隱性成本（訓練時間、上線初期生產力下降、既有流程的中斷）。效益也分兩類：(1) 硬效益（hard savings）——可直接量化的節省（減少兩名人力、庫存降低 30% 釋出現金、產能提升 15% 增加營收）；(2) 軟效益（soft savings）——間接且較難量化但確實在的改善（員工安全提升→職災補償減少、交期準確率提升→客戶留存率提高、流程標準化→訓練時間縮短）。軟效益容易被質疑「空泛」，必須用夠具體的邏輯鏈結證明它們最終轉化為財務影響。
- **實施計畫（implementation plan）**：把方案拆成可執行步驟，每個步驟的負責人、所需資源、時間估算、完成標準（deliverable）。一個出色的分析配上模糊的實施計畫，最終下場通常是漂亮的報告鎖在抽屜裡。
- **風險評估（risk assessment）**：方案失敗的可能原因有哪些？機率多大？影響多大？對策是什麼？很多人不願意主動談自己方案的風險，但專業的做法是**預先揭露風險並提出緩解措施**——這反而增加方案的可信度，因為顯示你已經周全思考過，而非一廂情願地樂觀。

### 1.6 實施與追蹤（Implementation & Follow-up）

許多 IE 專案死在這個階段——分析完美、建議合理、簡報精彩，然後……什麼改變都沒有發生。專案報告歸檔後，一切回到原狀。

實施階段的挑戰不在技術，在**人**：(1) **變革抗拒（resistance to change）**——現場作業員長年來用同一套方法做事，他們心裡明白這不是最有效率的方式，但改變代表不確定性（我學得會新方法嗎？新方法會不會害我達不到產量目標而被檢討？新流程會讓我的工作變得更累嗎？）。IE 不能只丟一份 SOP 就走人——你需要與第一線人員一起站在現場、示範新流程、觀察他們實際操作時遇到的困難、根據回饋調整設計（而不是堅持「我的分析是對的，你們照做就對了」）；(2) **管理者支持（management buy-in）**——改善方案即使獲得高層口頭批准，現場中階主管的態度才是關鍵：如果他不認為這件事是他的優先事項，他不會安排時間讓屬下配合、也不會在會議中追蹤進度。解法：在專案早期就讓中階主管參與問題定義（讓他們覺得「這是我的問題」而非「這是上面派下來的事」），並確保方案的績效指標（KPI）與他們被考核的指標對齊；(3) **永續機制（sustainment）**——改善完成後如何確保不會一段時間後又滑回原狀？只靠「希望大家繼續維持」是無效的——需要建立視覺管理（visual management）——現場的儀表板讓所有人一眼看見現狀是否在正常範圍內、定期稽核（audit）、以及將新的標準納入日常考核中。

**追蹤與控制**：專案實施後應設定一段追蹤期（如三個月），定期收集關鍵績效指標（KPI）數據，與基線比較確認改善效果是否持續。如果效果消退，回到問題定義階段重新檢視根因分析是否遺漏了什麼。這正是 PDCA 循環（Plan-Do-Check-Act）中 Check 與 Act 的體現——改善不是一次性事件，是持續循環的過程。

## 2. 系統思考與整合（Systems Thinking & Integration）

所有 IE 工具最終服務於一個目標：**理解並改善系統**。系統思考（systems thinking）是一套看世界的方式——它教你把眼光從個別零件移開，轉而關注**零件之間的連結、回饋、延遲與非線性**，因為這些互動關係才是系統行為的真正驅動力。

### 2.1 系統 vs 零件——整體大於部分的總和

一個經典的 IE 思維練習：在你的生產線上有五個工作站，加工時間分別是每件 10, 12, 8, 15, 11 分鐘。如果你單獨改善第三站，把它的加工時間從 8 分鐘降到 5 分鐘，整條生產線的產能會提升多少？**答案是零**——因為瓶頸在第四站（15 分鐘），你改善非瓶頸站只是在讓它閒置更久，沒有任何一單位額外的產出。這是最簡單的系統思維教訓：局部最佳化（local optimization）不一定轉化為全局改善（global improvement），甚至可能讓全局更差（當你在非瓶頸站投入資源擴充時，只是建立在製品庫存堆積）。

### 2.2 回饋結構——系統行為的深層原因

系統中的因果關係很少是單向的 A→B；更多時候是 A→B→C→A，形成**回饋迴路（feedback loop）**。回饋迴路可以分為兩類：

- **正回饋／增強迴路（reinforcing loop）**：系統往某個方向自我強化。例如：銷量增加→市場口碑擴散→更多人購買→銷量更增加（成長飛輪）。又例如：交期延誤→客戶取消訂單→營收下降→裁員→人力不足→交期更延誤（死亡螺旋）。正回饋使系統偏離均衡，往極端方向推。
- **負回饋／平衡迴路（balancing loop）**：系統往穩定均衡方向自我修正。例如：庫存低於安全存量→觸發補貨訂單→庫存回升→補貨停止。又例如：產出超過需求→成品庫存堆積→降價促銷去化庫存→產出降低。負回饋使系統趨向目標，是控制與調節的基礎。

IE 整合專題的核心技能之一是**畫出系統的因果迴路圖（causal loop diagram, CLD）**——把系統中關鍵變數之間的影響關係用箭頭標示（+ 表示同向變動、- 表示反向變動），然後辨識圖中的回饋結構。這個動作本身就能揭露許多直覺察覺不到的行為動態。例如：許多公司推「零庫存」政策→供應商為了準時交貨而加急（expensive premium freight）→供應商的利潤被侵蝕→供應商品質下降→客戶退貨增加→必須備更多安全庫存應急→庫存又回升。這個迴路告訴你：單一指標（庫存天數）的改善若沒有同時考慮對供應鏈上游的影響，可能最終反噬自己。

### 2.3 限制理論（Theory of Constraints, TOC）

Eliyahu Goldratt 提出的 TOC 是 IE 系統思維最實戰化的體現。TOC 的核心命題很簡單：**任何系統的產出受限於極少數瓶頸（constraint）；改善瓶頸以外的任何東西都是浪費**。

TOC 的五個聚焦步驟（five focusing steps）：
1. **識別瓶頸（identify the constraint）**：找出系統中限制整體產出的那個環節——最容易的方法是看「哪裡前面堆積最多在製品」——工件排隊最長的那一站就是瓶頸。
2. **充分利用瓶頸（exploit the constraint）**：在不增加投資的前提下，從瓶頸榨出更多產能：確保瓶頸站永遠有工件可做（不因缺料而閒置）、瓶頸站不停機用餐（讓作業員輪流休息）、不讓不良品流到瓶頸站浪費它的寶貴時間。
3. **所有其他環節服從瓶頸（subordinate everything else）**：這是反直覺的一步——讓非瓶頸站的排程全面配合瓶頸的節奏。非瓶頸站不該最大化自身產能（那只會堆積在製品），而是僅在瓶頸需要的時候才生產。**鼓–緩衝–繩（drum-buffer-rope, DBR）** 機制就是此步驟的具體化：瓶頸的節奏是「鼓」（drum），瓶頸前設置「緩衝」（buffer）確保它從不缺料，上游站由一條「繩」（rope）拉著——只有當緩衝被消耗時才觸發生產。
4. **提升瓶頸（elevate the constraint）**：前述步驟都沒用（或想追求更高產出）時，才考慮投資——買機台、加人力、外包、改設計。
5. **重複（repeat）**：瓶頸被打破後，系統中一定會有另一個環節成為新的瓶頸——**不要讓慣性變成下一個瓶頸**——回到步驟 1，重新識別新的限制。

TOC 對 IE 整合專題的意義：在資源有限的現實中，**知道不該做什麼與知道該做什麼同等重要**。TOC 提供了一個邏輯清晰的優先級框架，避免團隊掉入「到處改善、處處動一點、整體沒變化」的常見陷阱。

### 2.4 價值流圖（Value Stream Mapping, VSM）

價值流圖是精實生產中用以**可視化整個流程**的工具——它畫出從客戶下訂單到產品交付之間所有步驟，並區分哪些步驟是「增值（value-added, VA）」（真正在改變產品形態、讓客戶願意付錢的動作，如組裝、銲接、加工）、哪些是「非增值（non-value-added, NVA）」（傳送、等待、檢驗、搬運、堆積——客戶不會為這些付錢）。IE 整合專題常用 VSM 作為診斷起點：畫出當前狀態圖（current state map）→計算增值時間佔總前置時間的比例（在傳統製造中常見的數字是 < 5%）→識別最大浪費源→設計未來狀態圖（future state map）→推導改善計畫。

VSM 的價值不只是數據——把一群來自不同部門的人拉到一面大白板前，一起畫出整條價值流，這個過程本身就迫使所有人看到自己每天都在做、卻從未從頭到尾看清楚的全局。經常發生的情況是：銷售部門第一次知道自己的訂單在工廠裡經歷了哪些步驟、製造部門第一次發現自己的延誤如何影響終端客戶。

### 2.5 系統動力學入門（System Dynamics Primer）

前述的因果迴路圖是「質化」的系統思考——你可以看出變數之間相互影響的方向，但看不出量的大小與時間延遲的效果。系統動力學（system dynamics）加上**存量–流量結構（stock-flow structure）**：存量（如庫存、員工人數、累積經驗）是系統的「記憶」——它們是流量的積分 $Stock(t) = Stock(0) + \int_0^t (Inflow - Outflow)\,dt$。存量不會瞬間改變——你今天開始大量招聘，員工人數不會今天翻倍（有招聘與培訓延遲）；你今天停止進貨，庫存不會歸零（還有既有庫存要消耗）。這種存量–流量的延遲效果正是長鞭效應（bullwhip effect）的根本原因：零售端一個微小的需求波動，因為供應鏈上每一級都有庫存調整的延遲與過度反應，傳到上游製造商時被放大數倍。

對 IE 整合專題而言，系統動力學提供的核心洞見是：**問題的根源和問題的症狀，在時間與空間上通常不在同一個位置**。你今天看到的庫存暴增，可能是三個月前一個促銷決策引起的；今天某站的產能瓶頸，源頭可能是三週前一個物料規格的微調。如果你的分析只停留在症狀的時空範圍內，永遠找不到真正的根因。

## 3. 常見專題類型與對應方法論組合

IE 整合專題的應用場景非常廣泛，以下列舉五大常見類型，以及每種類型中 IE 工具箱的典型組合方式。

### 3.1 製造系統改善（Manufacturing System Improvement）

**典型場景**：一條組裝線的產能跟不上訂單成長、換線時間過長吃掉寶貴產能、在製品堆積如山但瓶頸站卻因缺料閒置。

**常用工具組合**：
- **流程分析**：先畫出當前狀態的價值流圖（VSM），計算各站加工時間（cycle time）與節拍時間（takt time = 可用生產時間 / 客戶需求數量）的關係。理想上各站加工時間應與節拍時間一致或略低——差異過大的站就是改善標的。
- **生產線平衡（line balancing）**：將總作業拆成最小的不可再分的「作業元素（task element）」，記錄每個元素的作業時間與先行關係（precedence——哪些必須在哪些之前完成），然後將作業元素分配到各工作站，使得各站總作業時間盡可能均等（最小化閒置時間），且不違反先行關係。這是一個組合最佳化問題——大規模時是 NP-hard，需啟發式演算法。線平衡的效率指標是**平衡延遲（balance delay）** $= 1 - \frac{\sum 各站加工時間}{站數 \times 最大站加工時間}$——越接近 0 越好。
- **快速換模（SMED）**：將換線作業分解為「內部作業」（internal setup——必須在機台停機時進行的，如拆裝模具）與「外部作業」（external setup——機台運轉中可以事先準備的，如預熱模具、備料、把下一批工件搬到機台旁）。SMED 的核心策略是盡可能把內部作業轉為外部作業（例如將模具預先鎖在備用夾具上，換模時直接整組替換而非現場調整），再優化剩餘內部作業的動作（標準化程序、快速夾具、平行作業——兩人同時進行兩側的拆裝）。典型的成果是把換線時間從數小時壓縮到數分鐘（single-minute——即 SMED 名稱由來）。
- **產能模擬**：用離散事件模擬驗證改善後的產線設計——加入隨機因素（機台故障、作業時間變異、不良率）後，產能還能不能達標？瓶頸會轉移到哪裡？

### 3.2 物流與供應鏈專題（Logistics & Supply Chain）

**典型場景**：倉庫揀貨效率瓶頸、庫存水準過高佔用現金但服務水準卻不理想、配送路線成本居高不下。

**常用工具組合**：
- **庫存政策最適化**：用 ABC 分類區分管理策略——A 類高價值高周轉品用嚴格的連續盤點 + 安全庫存精算（如需求量與前置時間都為隨機時的安全庫存公式 $SS = z_{\alpha} \sqrt{L\sigma_D^2 + D^2\sigma_L^2}$，其中 $z_{\alpha}$ 是服務水準對應的標準常態分位數）；C 類低價值品用簡化的定期盤點（periodic review）降低管理成本。
- **網路最佳化**：倉庫該設幾個、設在哪裡？用設施選址模型（facility location）——通常是以總物流成本（運輸 + 倉儲營運）最小化為目標的 MILP 模型：決策變數包含是否在候選點開設倉庫（二元變數）及每家倉庫服務哪些客戶（分配變數）。
- **車輛路徑問題（VRP）**：用啟發式演算法（節省法 Clarke-Wright savings algorithm + 2-opt/3-opt 局部搜尋）產生可行路徑、再用模擬驗證執行細節（一天內各路徑的實際工時是否超過司機法定上限）。
- **供應鏈模擬**：用系統動力學或離散事件模擬重現多階供應鏈的行為，測試不同的補貨規則（如每一級是「依下游訂單拉動」還是「依自身庫存水位推動」）、資訊共享程度（下游需求對上游是否透明）對長鞭效應的抑制效果。

### 3.3 服務系統專題（Service Systems）

**典型場景**：醫院急診室等待時間過長、客服中心的應答水準（service level——例如 80% 的來電在 20 秒內接聽）不達標、機場安檢通道排隊堵塞。

IE 方法的獨特價值：服務系統的「產品」是無形的（諮詢、診斷、服務），且顧客本身參與在流程中——你不能預先生產「服務」來庫存，必須在需求到來的瞬間就提供產能。這使服務系統對變異特別敏感。

**常用工具組合**：
- **排隊分析 + 模擬**：先用排隊理論估算穩態績效（平均等待時間、隊列長度、服務水準），確認假設是否合理（到達過程是否接近卜瓦松、服務時間是否接近指數分布）；若實際系統太複雜（多重服務階段、顧客中途離開、不同優先級），再用離散事件模擬細部驗證。
- **人員排班最佳化**：服務需求隨時間劇烈波動（客服中心早上 9–11 點是尖峰、餐廳午餐時段爆量、醫院急診週末晚上最忙）。目標是設計班表（每位客服人員的上班時間與休息時間），使得每時段的當班人數 >= 該時段預估所需人數（由排隊模型推導——「滿足服務水準所需的最少人數」），且總人力成本最小。這是一個典型的集合覆蓋（set covering）或整數規劃問題。
- **流程改造**：用 VSM 畫出服務流程（例如從病人掛號到見到醫生之間的所有步驟）→識別浪費（等待、重複填表、資訊傳遞延遲）→設計精簡後的未來狀態。服務流程的浪費常比製造流程更嚴重且更隱形——因為沒有實體的在製品堆積在眼前提醒你，浪費以「時間」的形式存在（顧客在等候區滑手機、文件在主管的待簽匣裡躺三天）。

### 3.4 品質改善專題（Quality Improvement）

**典型場景**：某產品線的退貨率居高不下、關鍵尺寸的製程能力 $C_{pk}$ 低於 1.0（表示不合格率過高）、客戶抱怨集中在特定失效模式。

IE 整合專題中的品質改善通常採用 **DMAIC 架構**（Six Sigma 的核心方法論）：
- **Define**：定義問題範圍、客戶的品質要求（CTQ: critical-to-quality）、專案目標。
- **Measure**：確認量測系統可靠（先做量測系統分析 MSA 中的 Gage R&R——確認同一檢驗員重複量測的一致性及不同檢驗員之間的一致性），再收集基線數據，計算現有製程能力 $C_{pk} = \min\!\left(\frac{USL-\mu}{3\sigma}, \frac{\mu-LSL}{3\sigma}\right)$——分子是「平均數離規格界限還有多遠」，分母是「變異有多大」。$C_{pk} \geq 1.33$ 是一般認可的合格水準。
- **Analyze**：用魚骨圖（Ishikawa diagram）或 FMEA 識別潛在根因→用統計檢定或迴歸分析確認哪些因子對品質有顯著影響→用 Pareto 圖排序根因的重要性（80/20 法則——少數根因解釋多數失效）。
- **Improve**：針對確認的根因設計改善方案——可能是製程參數調整（用 DOE 找出最佳參數組合）、防呆裝置（poka-yoke——讓錯誤物理上不可能發生，例如設計模具使工件只能以正確方向放入）、或標準作業程序修訂。
- **Control**：建立管制圖（control chart）持續監控關鍵品質特性，確保改善效果不會隨時間消退。管制圖的邏輯：監控統計量（如 $\bar{X}$ 與 $R$）是否落在管制界限內——若出界，表示有特殊原因變異（special cause）介入，須立即調查。

### 3.5 設施規劃專題（Facility Planning）

**典型場景**：工廠因訂單成長需要擴大產線、新倉庫的內部布局設計、辦公空間的重新配置以促進部門間協作。

**常用工具組合**：
- **SLP 系統化布局規劃**（見第 12 科設施規劃與物流筆記中的詳述）——從物流強度與非物流關係出發，逐層建構布局方案。
- **從至表（from-to chart）**：記錄各作業區之間的物流量（每日搬運次數或重量），作為布局最適化的基礎資料。
- **模擬驗證**：將候選布局方案建入離散事件模擬模型，評估在真實的隨機波動下（機器故障、訂單變動），物流是否順暢、瓶頸是否可控。布局紙上好看、模擬跑出來塞車——這種情況極其常見，因為靜態的距離矩陣無法反映動態的互動擁擠。
- **投資分析**：設施規劃通常涉及鉅額資本支出（蓋廠房、買設備、移機），必須搭配工程經濟分析（NPV、IRR、回收期）證明方案在財務上可行。

## 4. 專案管理基礎（Project Management for IE Capstone）

整合專題本身就是一個專案——你（與團隊）要在有限的時間與資源內，從零開始交付一個有品質的成果。這個過程也需要被管理。

### 4.1 工作分解結構（Work Breakdown Structure, WBS）

WBS 是把專案拆成一層層可管理的「工作包（work package）」的階層式結構。拆分的原則：每個工作包的範圍明確到「可以指派給一個人、可以估算工時與成本、完成與否可以客觀判斷」。對 IE 整合專題而言，典型的頂層分解可能是：(1) 問題定義與文獻回顧、(2) 資料收集、(3) 資料清理與 EDA、(4) 模型建構、(5) 模型驗證、(6) 情境分析與最佳化、(7) 建議方案撰寫、(8) 簡報製作、(9) 最終報告撰寫。

WBS 最重要的原則：**100% 規則**——下一層的工作包加總必須等於上一層工作的全部範圍，不能有遺漏也不能有重疊。另一個常犯的錯誤是把 WBS 寫成待辦清單（「討論方案」「約訪談」）而非可交付成果（deliverable-oriented）——WBS 的每個節點應該是一個產出物（一份數據集、一個模型、一份報告章節），它才有辦法被驗證完成。

### 4.2 時程管理：甘特圖與要徑法（Gantt Chart & CPM）

- **甘特圖**：以時間為橫軸、任務為縱軸，用長條顯示每項任務的起迄時間。它的價值是**可視化**——整個團隊一眼看到現在該做什麼、誰負責什麼、不同任務之間的時間重疊如何。
- **要徑法（critical path method, CPM）**：當任務之間有依賴關係（WBS 中某些工作必須等前一個工作完成才能開始），要徑是從專案開始到結束之間「最長的那條依賴路徑」——要徑上的任何任務延誤，整個專案就會延誤；非要徑任務則有「浮時（float / slack）」——它可以延遲若干時間而不影響最終期限。CPM 告訴專案經理該把管理注意力集中在哪裡：**盯緊要徑上的任務**，其他任務有浮時可以容錯。

PERT（program evaluation and review technique）進一步納入不確定性：對每項任務估計樂觀時間 $a$、最可能時間 $m$、悲觀時間 $b$，將任務工期視為 beta 分布的隨機變數，期望工期 $t_e = (a + 4m + b)/6$。多條平行要徑交會時，可計算專案在特定期限內完成的機率。

### 4.3 利害關係人管理（Stakeholder Management）

IE 整合專題的利害關係人通常至少包含：指導教授（在乎方法論的嚴謹性）、業主／合作單位（在乎方案實用性與成本）、團隊成員（在乎工作量分配公平與學習收穫）。這三種人對「好專案」的定義不同——教授看方法論深度與原創性、業主看省了多少錢或解決了多少痛點、團隊看過程是否順利。專題成功的關鍵之一就是**管理各方期望**——在專案初期就明確溝通「這個專案會產出什麼、不會產出什麼、誰決定優先級」，避免後半段被突襲式的要求變更（scope creep）。

### 4.4 三重限制與取捨（Triple Constraint）

任何專案都受限於三個維度：**範疇（scope）**、**時間（time）**、**資源（resources）**。三者構成鐵三角——你不可能同時最大化三者。如果你要在更短時間內完成，你要麼縮小範疇、要麼增加資源（人、錢）。專題最常見的失誤是：在初期設定了過於野心的範疇（「我們要同時改善產能、品質、庫存、與人員滿意度」），到了中期才發現資料收集就耗掉一半時間，最後只能草草收尾。好的專案管理是在初期就設定一個**最小可行範疇（minimum viable scope）**——必須完成的核心部分——然後把時間與資源預留緩衝給這些核心任務，有餘裕再擴展。

### 4.5 IE 專案適合哪種管理方式

IE 整合專題的性質——資料收集與分析需要時間、建模與驗證之間有自然的依賴關係、最終交付物的品質高度仰賴反覆修正——通常更適合**混合式（hybrid）管理**：用瀑布式（waterfall）架構規劃整體階段（必須先有問題定義才能收集資料、必須先有資料才能建模——這些階段之間的依賴是剛性的），但在每個階段內採用敏捷（agile）精神——例如建模階段可能經歷數個「建模→驗證不佳→修正模型」的短循環；報告撰寫階段可能每週疊代一個章節，交給指導教授或同儕審閱修改。純敏捷對 IE 專題並不實際——你不能在「對問題還沒有完整認識」時就開始建模，然後每兩週交一個可用的部分給客戶看——IE 的分析通常需要先有完整的數據基礎，否則模型跑出來是 garbage in, garbage out。

## 5. 溝通與呈現（Communication & Presentation）

IE 工程師的悲劇：做了一整學期嚴謹的分析，但因為簡報與報告無法有效傳達分析結果，導致方案不被採納。技術溝通能力不是軟技能——它是專業能力的延伸：**你不能有效地溝通你的分析，就等於沒有做分析**。

### 5.1 書面報告——從執行摘要開始

決策者（忙碌的主管）讀報告的方式與你寫報告的方式完全相反：你從問題定義、文獻回顧、資料方法、分析結果、一路寫到結論；他們先看**執行摘要（executive summary）**，如果在摘要中找不到他們想要的資訊，報告就被擱置了。

一個好的執行摘要必須**獨立存在時仍有完整意義**：

- 一句話描述問題與其重要性
- 概述你的方法（不是詳細步驟，而是方法邏輯——「我們分析了過去兩年的生產數據並建立了離散事件模擬模型來驗證三種改善方案」）
- 核心結果（數字——「方案 B 可將瓶頸站產能提升 18%」而不只是「方案 B 有顯著改善」）
- 建議與財務影響（「建議採用方案 B，初期投資 $50,000，預估年省 $200,000，回收期約 3 個月」）
- 限制與下一步（誠實——「此分析基於 2025 年數據，建議在 2026 Q1 重新校驗參數後再實施」）

整份報告應遵循**金字塔原理（pyramid principle）**：先給結論，再展開支持結論的證據與推理。讀者不是從頭讀到尾——他們先讀摘要，然後跳到他們最關心的章節（財務影響、實施計畫）。報告的結構應該支援這種跳躍式閱讀——每個章節應該有自己獨立的「本章摘要」概念。

### 5.2 數據視覺化原則

圖表的目的不是「讓報告變漂亮」，而是**讓數據中隱藏的結構、趨勢、比較關係瞬間浮現**。

- **選對圖表類型**：比較不同類別 → 長條圖（bar chart）；顯示時間趨勢 → 折線圖（line chart）；顯示構成比例 → 堆疊長條圖或圓餅圖（pie chart 僅適合 3-5 個類別）；顯示兩個連續變數的關係 → 散佈圖（scatter plot）；顯示分布形狀 → 直方圖（histogram）或箱形圖（box plot）。
- **不要誤導**：Y 軸不從零開始會誇大差異；雙 Y 軸容易夾帶人為操控（調整兩軸範圍讓兩條線看起來有意義地交錯）；3D 效果純粹增加視覺噪音、扭曲數據解讀。
- **IE 特有的圖表類型**：(1) **柏拉圖（Pareto chart）**——長條圖 + 累積百分比折線，一眼看出「少數根因佔多數影響」，是品質改善報告的必備圖；(2) **龍捲風圖（tornado diagram）**——將敏感度分析中多個參數的影響範圍水平排列，最寬的條在最上面——直接傳達「哪些因素最重要」而不需要讀者理解敏感度分析的數學細節。

### 5.3 口頭簡報——說故事，不要念數據

技術人員最常犯的簡報錯誤是把簡報當成「濃縮版報告」——每張投影片塞滿文字、小字體、複雜的表格，然後逐字念給聽眾聽。這對聽眾是折磨。

好的 IE 簡報是一場**敘事（narrative）**，結構類似推理小說：(1) 設定場景——「我們觀察到 XX 系統有個問題，它的影響有多大（一個令人印象深刻的數字）」；(2) 展開調查——「我們怎麼收集資料、我們發現了什麼有趣（甚至反直覺）的現象」；(3) 提出見解——「我們的模型告訴我們，真正的原因不是大家原本以為的 A，而是 B」；(4) 給出方案——「所以我們建議做 C，成本這麼多、效益這麼大、風險在此，可控的方法是…」；(5) 呼籲行動——「我們需要您現在就決定的是…」。

不同聽眾要調整語言與深度：(1) 對技術同儕（你的教授與同學）——可以深入方法論，展示你對工具的掌握；(2) 對管理層——談數字（成本、時間、影響），不要談方法論細節。他們不需要知道你的模擬模型用了什麼亂數生成器——他們需要知道模型的結論可信、方案的財務可行性如何；(3) 對現場操作人員——聚焦在「你的日常作業會怎麼改變、為什麼這個改變讓你的工作更容易（或至少不更難）、遇到問題找誰」——操作人員是方案的最終執行者，他們的買單與否直接決定了專案的成敗。

### 5.4 一頁備忘錄（One-Page Memo）原則

這是 Amazon 內部的著名溝通紀律：所有重要的提案必須能用一頁（或六頁敘事文，但概念相同）講清楚。對 IE 整合專題而言，這個原則強迫你把思考淬煉到最純粹的狀態：如果你的方案無法在一頁紙上讓一位不具備 IE 背景但頭腦清楚的人理解並信服，那你要麼分析還不夠扎實（所以必須用大量術語虛飾）、要麼還沒想清楚真正的重點在哪裡。

## 6. 倫理與專業責任（Ethics & Professional Responsibility）

工程師的最終責任不是對雇主，而是對**公眾的安全、健康與福祉**——這是所有工程倫理守則的第一條。IE 的工作雖然不直接涉及橋樑會不會垮、飛機能不能飛，但 IE 做出的決策（裁員、外包、改變工作設計）直接影響活生生的人的工作與生計，因此 IE 的倫理責任雖然形式不同，份量並不輕。

### 6.1 數據誠信（Data Integrity）

IE 分析仰賴數據，而數據可以被有意或無意地操弄來支持預設的結論。幾種常見的倫理陷阱：(1) **只挑有利的數據（cherry-picking）**——你跑了五種模擬情境，只報告支持你偏好的方案的那一種，對其他四種閉口不提；(2) **p-hacking**——對同一組數據反覆跑不同統計檢定，直到找到一個 p < 0.05 的結果就報告它「顯著」——但因為你跑了很多次，這個「顯著」純屬隨機（多重比較問題）；(3) **隱藏假設**——你的最佳化模型倚賴「需求量在未來五年穩定以每年 3% 增長」這個假設；如果你不提這個假設，讓讀者以為結論是穩健的，這是不專業的——必須主動揭露主要假設，並做敏感度分析展示結論在不同假設下的穩健程度。

**專業準則**：你的目標不是讓某個方案「看起來最好」；你的目標是如實、全面地呈現分析結果，幫助決策者做出**知情的決策**。如果你發現自己的結論與出資者（公司主管、合作廠商）的期望相反，你的責任不是扭曲結論去迎合，而是用數據說服對方——如果說服不了，最少要確保你的分析報告中有書面紀錄你的專業判斷，讓時間來證明誰是對的。

### 6.2 模型與分析的限制（Acknowledging Limitations）

任何模型都是對現實的簡化——這本身不是問題，問題在於**不告知使用者簡化了什麼**。一個稱職的 IE 分析師應該在報告中明確列出：(1) 模型有哪些簡化假設（例如假設機台故障間隔為指數分布——真實情況可能是 Weibull 分布有老化效應）；(2) 這些假設可能在什麼情況下失效（市場需求突然轉變、供應鏈中斷、新法規上路）；(3) 若假設失效，結論會往哪個方向偏（過度樂觀還是過度保守？）。

### 6.3 社會與環境責任（Social & Environmental Responsibility）

IE 的典型決策——導入自動化取代人力、將生產線移到勞動成本更低的國家、減少庫存以降低營運資金——都有社會與環境的外部性（externality）：

- **自動化與就業**：從企業角度，自動化提升效率、降低成本——這是 IE 存在的基本價值。但從社會角度，自動化可能消滅特定類型的就業機會（重複性裝配作業），而這些工作往往是低技能勞工唯一可以從事的。倫理上 IE 的責任不是拒絕自動化，而是在規劃時納入**社會影響評估**——自動化釋出的人力是否可以重新培訓轉移到更需要判斷力的崗位（如品質稽核、流程改善、設備維護）？實施節奏能否配合自然的員工流失（退休、自願離職）而非直接裁員？
- **全球供應鏈與勞動條件**：選擇最低成本的供應商是 IE 供應鏈管理的核心邏輯——但這個供應商的低成本是否建立在剝削勞工、忽略安全、破壞環境的前提上？專業 IE 應該將供應商的社會與環境合規性納入供應商評選的評分維度（而不僅僅是價格、交期、品質）。
- **永續與循環經濟**：IE 傳統的生產系統設計追求「線性經濟」——原料開採→製造→使用→廢棄。但地球的資源與廢棄物吸收容量是有限的。循環經濟（circular economy）重新設計系統使材料在技術循環（回收再製、再使用、再製造 remanufacturing）或生物循環（堆肥回歸自然）中持續流動。IE 在其中的角色：用生命週期評估（life cycle assessment, LCA）量化產品從原料到廢棄的完整環境足跡、用逆物流（reverse logistics）設計回收體系、用物料流分析確保回收材料能追溯且品質可控。

### 6.4 專業認證與持續學習

IE 不是一個被嚴格管制的執業（不像土木工程或藥劑師那樣需要法定執照才能執業），但仍有多種專業認證可強化你的專業信任度：

- **PE（Professional Engineer, 專業工程師）**：在美國由各州頒發，需通過 FE（基礎）與 PE（專業）考試並具備數年工作經驗。IE 的 PE 考試涵蓋作業研究、生產系統、品質工程、工程經濟等。PE 是競標政府合約或簽署設計圖面的法定資格。
- **六標準差黑帶（Six Sigma Black Belt, SSBB）**：證明你在 DMAIC 方法論、統計分析與改善專案領導上的能力。ASQ（American Society for Quality）的 SSBB 認證是最受認可的版本。
- **PMP（Project Management Professional）**：跨產業的專案管理認證，對於 IE 在大型改善專案中擔任專案經理或 PMO 角色有幫助。
- **CQE（Certified Quality Engineer）**：專注於品質系統的設計、實施與稽核。

無論是否有認證，IE 作為一個與技術、管理、社會三者交界處的專業，要求從業者在整個職涯中**持續學習**——製程技術在進化（積層製造、協作機器人、物聯網）、管理思維在演變（敏捷、設計思考、OKR）、社會對企業責任的期望在提高（ESG、DEI）。大學教育給你的是學習框架與基礎——真正的能力是在職場上遇到新問題時，知道如何快速拆解、找到對的工具、並做出數據驅動的判斷。

## 碩士 / 博士層級延伸

**碩士層級**（較深入，但仍在一個子領域內）：
- **高等系統工程（advanced systems engineering）**：將系統的「湧現行為（emergent behavior）」——也就是無法從個別零件推導出的系統整體行為——做系統性的建模。應用於大型基礎建設（智慧電網、城市交通系統）的規劃與韌性評估。
- **企業轉型（enterprise transformation）**：不只改善一個工廠或一條產線，而是在整個企業的層級推動營運模式的根本變革——例如從「大量生產→大量客製化」或從「賣產品→賣服務」（servitization，例如引擎製造商不賣引擎，改賣「飛行時數」——按實際使用收費，維修與可靠度由製造商負責）。
- **工業 4.0 / 5.0 部署方法論**：如何從現有的傳統工廠（棕地 brownfield）逐步導入物聯網感測器、邊緣運算、數位孿生與 AI 決策輔助——不是買一堆技術堆上去就叫工業 4.0。關鍵是**數據基礎設施（data infrastructure）**的建立——感測器的標準化、資料流的拓撲設計、IT/OT 融合架構。
- **永續工業系統（sustainable industrial systems）**：將生命週期評估（LCA）與傳統的 IE 決策模型（設施選址、供應鏈設計、製程選擇）結合——例如在供應鏈網路的 MILP 模型中除了物流成本與碳排放成本（碳稅／碳權）也設為目標函數的一部分，求解「最低總社會成本」的供應鏈配置。
- **高等模擬最佳化（advanced simulation optimization）**：當你的系統只能用模擬評估（沒有解析的目標函數），但仍要找出最佳參數組合時——用元啟發式（genetic algorithm, particle swarm, simulated annealing）或貝氏最佳化（Bayesian optimization——用高斯過程（Gaussian process）代理（surrogate）昂貴的模擬目標函數，逐步在最可能有改善的點上評估）來導航模擬實驗，取代傳統的 trial-and-error。

**博士層級**（研究方向列表）：
- 數位孿生驅動的自主決策閉迴路（digital twin-driven autonomous decision closed-loop）——工廠自主偵測異常→自主診斷根因→自主生成修復計畫→自主調度資源執行，人類僅在例外時介入
- 可重構製造系統（reconfigurable manufacturing systems）——模組化機台可快速重組以適應產品變更，對應的排程與控制演算法
- AI 強化的即時排程（AI-augmented real-time scheduling）——深度強化學習（deep RL）在高變異製造環境下的動態派工決策
- 循環供應鏈的網路設計（circular supply chain network design）——同時最佳化正物流（原料→生產→消費者）與逆物流（消費者→回收→再製），兩者之間的交互作用
- 人機協作系統的作業設計（human-robot collaboration system design）——在協作情境下同時考量機器人效率與人類人因負荷的工作分配最佳化
- 社會–技術系統的韌性工程（resilience engineering for socio-technical systems）——當系統由人、組織、技術三方交互構成時，如何量化與提升系統面對突發事件的吸收與恢復能力
