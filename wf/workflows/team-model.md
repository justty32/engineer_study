# team-model — 誰來做：角色三層、聰明度分級、選人判準

[WORKFLOWS](../WORKFLOWS.md)｜[INDEX](../INDEX.md)

本檔記**誰來做**——分幾層角色、每層派哪一級的模型、按什麼順序選人。**怎麼做**在別處：切線與交接書見 [dispatch](dispatch/README.md)，資源鎖見 [resources](resources.md)，通訊見 [inbox/PROTOCOL](inbox/PROTOCOL.md)。

**何時用**：要開一個 agent 團隊、要決定某一層派哪級模型、要按用途分角色。
**何時不用**：只有一條線、一兩個檔的小改（見 [dispatch](dispatch/README.md) 的「何時不用」）；只是要送一則情報 → [inbox](inbox/README.md)。

## Done when

- 下方分級表與消耗速度表已按**你自己的模型清單**填完。
- 這一輪要開的每一層都**指名了誰**——頂層、領導、工人各自是哪一格。

## 一、角色三層

### 頂層 agent（使用者直接面對的那一個）

職責四件：接收指令、開 agent 團隊、傳達指令、**協調使用者自己也會用到的資源**（鍵盤滑鼠螢幕，乃至 CPU、硬碟、網路）。**資源授權的源頭是使用者**——頂層只是代為分配，**不能自己創造授權**。

頂層只轉達與調度，**比領導笨是正常的**：計畫不在頂層做。

對使用者說話要**適合使用者理解**：初次出現的東西先用白話講一句。**預設不必翻譯**；只有使用者說今天不想動腦才逐項翻，翻譯本身吃太多 context 時，改成直接指出**該先看哪些檔**。

頂層通常可以有**自己的私人輔助者**（查資料、盤點），不必事事經過領導。輔助者**不算團隊 headcount**，數量由使用者指定，**沒指定就默認兩個**。

平時**不掛信箱醒鐘**、不逐則讀信——那是領導的事。**例外**：團隊裡有外部 agent 要直接找頂層時，頂層也要盯自己的信箱（見第七節）。

### 團隊領導（＝計畫制定者）

職責：把目標拆成計畫、寫交接書、派工、監看、核驗、收線。

負擔重（計畫＋指揮＋匯報），所以**模型下限比工人高**——這一層要先訂一個下限級別，不從便宜格裡挑。**若「制定計畫」被分出去給某個成員，領導只剩指揮與匯報，就可以降一級。**

**跨體系的 agent 不建議當領導**：即使有 inbox，和頂層溝通仍然有成本。

兩條實務提醒：交接書的**範圍詞會被線遞移展開**，範圍要用排除法寫死、**件數 gate 與容量 gate 並列**（見 [dispatch](dispatch/README.md)）；領導自己 context 吃緊時**寫 state 檔交棒**，不硬撐。

### 工人

依任務難度／內容，加上**使用者給的 headcount**，配便宜模型。工人自己再開子 agent **我們不管**——它在那一層就是領導；我們只告訴它**那邊能用多少資源**。

## 二、聰明度分級（總分）

本表 **project-owned**（2026-09-18 定案，理由在 [decisions](decisions.md)）。級別是使用者定的總分，不是某一項能力的分數；新增用途欄時只加欄、不改既有級別。

| 級 | 誰 | 用途細分 |
|---|---|---|
| A | Claude Opus 5 | 頂層（指揮／彙整／決策，不親自動手）；領導（架構師寫 BRIEF／SPEC、建置指揮官、獨立驗收者）；普通任務工人（章節作者、整理批次、寫筆記） |
| B | Claude Sonnet 5 | 簡單任務工人：機械複製、格式修正、清單盤點、唯讀掃描與取證（id 比對、編碼／殘留掃描、行數統計、信件初讀摘要）；**無寫入權的雜工**優先派它 |
| B（可選） | codex CLI（gpt-5.x，預設模型）| 可選的批次章節作者：額度大、能 headless 大量生 HTML；錯字、簡體字與算術照抄需獨立驗收，不當領導、不碰 `app.js`／`styles.css`。呼叫細節見 [interactive-study-site/build-with-agents/codex-notes.md](interactive-study-site/build-with-agents/codex-notes.md) |

## 三、token 消耗速度

兩條規則：

- **同一廠商內**通常**與聰明度成正比**——越聰明越貴。
- **不同廠商的同級模型可以差到兩級**，所以這張表**要自己實測填**，不能照抄別人的。

重點是推導出來的那一格：**「聰明度高、消耗速度低」的那一格就是性價比之神，工人層大量用它。**

本表 **project-owned**；消耗速度**未實測**，填「未測」的格子不要拿來排時程，實測後再填。

| 模型 | 聰明度 | 消耗速度 | 結論 |
|---|---|---|---|
| Claude Opus 5 | A | 未測（同廠商內最貴）| 頂層、領導、需要判斷的工人；不拿來做機械複製 |
| Claude Sonnet 5 | B | 未測（同廠商內比 Opus 便宜）| 簡單任務與唯讀雜工主力；目前的「性價比之神」候選，實測後確認 |
| codex CLI（gpt-5.x）| B | 未測（額度另計，不占 Claude 用量）| 可選批次章節作者；用它時驗收層一定要是 Opus |

## 四、選人判準（按序看這六項）

1. **任務難度／內容**——決定聰明度下限。
2. **使用者給的 headcount**——外生的上限，**不自己加碼**。
3. **token 消耗速度**——所以工人層大量用便宜模型，貴的留給真的需要的那幾件。
4. **溝通方便與否**——跨體系即使有 inbox 仍有成本，所以**領導層不建議跨體系模型**。
5. **管理上限**——**開太多領導不好管**；寧可少開領導、把量壓在工人層。
6. **時程**——用「產出速度 × 繞圈數 × 模型癖好」反推每段派誰、排多久，算法見 [speed](team-model/speed.md)。

## 六、context 管理

每層管自己下級的 context——管得好就是清雜訊，直接提升決策品質。五條規則見 [context](team-model/context.md)。

## 七、信箱——每個角色一格

角色分層之後通訊也跟著分層：每個 agent 一格，開團隊再配團隊一格。

三層各自哪些 STATUS 要醒、其餘怎麼辦，以 [inbox/wake-policy](inbox/wake-policy.md) 的策略表為準，本檔不重述。只有一條是本檔的：**領導上呈時重寫標題、帶自己的判斷，不是原文轉貼。**
