# plain-explain — 把陌生技術主題講成零基礎讀得懂的文字

[WORKFLOWS](../WORKFLOWS.md)｜[INDEX](../INDEX.md)

把一個讀者完全陌生的技術主題，寫成**不假設未聲明先備知識**的講解：名詞與概念分開教、術語中英對照、每個結論沿因果鏈推、每句話給得出可觀察證據。產物是**文字**（一份 `.md`、或既有文件裡的一節），不是網頁。

**何時用**：使用者說「這個我完全看不懂」「用白話講」「不要一堆看不懂的縮寫」「先講為什麼」；或既有材料只有定義、沒有因果。
**何時不用**：讀者已有模型、只要壓縮重點 → 走摘要（knowledge 包的 digest）。要做成可操作、會即時回饋的網頁課 → [interactive-study-site](interactive-study-site/README.md)。查一次就忘的事實直接查。

## Done when

- 講解檔存在，且下方「讀者基線」表每欄非空。
- 每個名詞在名詞表有列、每個概念在概念表有列，兩表沒有空欄。
- 首次術語格式自檢無漏網：`grep -noE '[A-Za-z][A-Za-z0-9.-]{2,}' <檔> | head -50` 逐一確認都已在首次出現處展開成 `繁中（English, ACR）`。

## 流程

1. **填讀者基線**：先寫下讀者會什麼、不會什麼、哪些名詞已造成理解債。這張表是後面所有取捨的依據；沒填就開始寫，必定寫成給同行看的東西。
2. **拆名詞與概念**：把主題拆成「名詞清單」與「概念清單」兩份，**分開**填下面兩張表。混在一張定義卡裡是本工作流第一號反模式。
3. **排依賴**：畫概念依賴——每個概念真正需要的**最少**前置。從讀者真正缺的底層開始，不從課綱標題開始。
4. **逐節寫**：每節照「固定順序」八步走，不跳步。
5. **收尾自檢**：過一遍反模式清單，跑 Done when 的 grep。

## 讀者基線

本專案的預設讀者＝擁有者（背景見 [PROJECT-GUIDE](../PROJECT-GUIDE.md)「擁有者背景」），每份講解與每門課都沿用這張表；某份講解的讀者不同就在該檔頭另寫一張。

| 項目 | 內容 |
|------|------|
| 已會什麼 | 軟體能力很強（會寫程式、懂資料結構與系統概念）；大學讀電機、特化通訊，名詞多半認得 |
| 不會什麼 | 軟體以外的學科在學時多有被當，基礎不扎實：電機／通訊等「本科」領域也不能假設已有穩固模型，要從基本觀念把脈絡講清楚 |
| 理解債名詞 | 認得字但說不出「為什麼」的工程名詞（例：摺積、阻抗匹配、零極點、建立／保持時間、雜訊裕度）；各課在 `PROJECT-BRIEF.md` 逐課列 |
| 學完要能做什麼 | 對各工程學科建立概論式認識：能解釋核心概念的因果、手算一組典型數值、判斷簡化模型在什麼範圍成立 |
| 不教什麼 | 不做完整參考資料、不深入碩博層級推導（只列方向）、不教廠商特定設定；軟體相關概念講精簡即可 |

## 語言與名詞契約

- 正文以**繁體中文**為主（含網站的按鈕、回饋與導覽文字）；標準名稱、程式識別字與必要原文保留英文。台灣慣用語優先，中國用語（觸發器、鎖存器、寄存器、時鐘…）列為錯字掃描項；譯名有分歧時由 Lead 裁決並記 [decisions](decisions.md)。
- 術語首次出現寫成 `繁中（English, ACR）`，例：`年均複合成長率（Compound Annual Growth Rate, CAGR）`。縮寫首次出現必須同時展開**繁中意思與英文全名**，後文才可只寫縮寫。
- 沒有穩定譯名時，先講**白話動作**，再保留業界英文。不能用一個英文名詞片語取代解釋。
- **類比只搭橋**：比喻之後一定要回到真實的機制、狀態、資料或數字，並講出比喻在哪裡失效。
- 同一份材料裡同一個概念只用一種叫法；換詞就是新增理解債。

## 兩種條目：名詞 vs 概念

兩者**不可混為一張定義卡**。名詞回答「這個詞指什麼」，概念回答「為什麼會這樣」。

**名詞條目**（填成表，一詞一列）：

| 名稱（繁中／English, ACR）| 白話：它實際做什麼 | 位置／層級：存在哪裡、誰用它 | 機制：靠什麼生效 | 不要混淆：與哪個相鄰名詞的邊界 |
|---|---|---|---|---|

**概念條目**（一概念一小節，六段固定）：

```text
問題：讀者真正想知道的 why（用讀者的原話，不要先改寫成課綱標題）
角色與前置：誰參與、先要有什麼
因果：輸入／事件 → 機制 → 狀態或資料流如何改變
結果：系統、使用者、下游（資安主題：攻擊者）看到什麼
證據：可由哪種紀錄、log、封包、儀器量測、檔案或流程驗證
反例：最容易誤套的相似情況
```

名詞跨兩節以上反覆出現、易混淆、或總量約 15 個以上時，把名詞表抽成獨立的可搜尋字典檔。字典是**回查用**的，不要求讀者背完才准往下讀。

## 通用因果骨架

每個技術概念固定沿這條鏈講，缺一環就是還沒講清楚：

```text
目標／資產與系統邊界
  → 哪個角色、輸入、事件或前置條件出現
  → 真實機制如何處理它
  → 資料流、控制流或系統狀態如何改變
  → 對使用者、系統或下游造成什麼結果
  → 能從紀錄、輸出、檔案、資料或量測看到什麼證據
```

領域專屬的細節在各節裡補，不改這條主鏈：硬體／物理主題把「機制」講到電源、參考點、回路與能量去向（見 [PRINCIPLES-FIRST](interactive-study-site/PRINCIPLES-FIRST.md)）；網路安全主題再明確標出資產、身分、actor、攻擊者能力、信任邊界、控制措施，以及機密性／完整性／可用性受到的影響。主題若有**可量測的量**（時間、金額、比例、成功率…），最後那一環要具體到「用什麼工具看、看到什麼數字」，不能只寫「可以驗證」。

## 每節固定順序

1. 讀者的 **why 問題**（原話）。
2. **一句話答案**。
3. **最少前置**：這節假設已懂什麼，各連回哪裡。
4. **因果鏈**：照上面的骨架走完。
5. **例子**：至少一組具體數值或具體情境，能手算就手算一次。
6. **易混**：明確拆開最容易混淆的相鄰概念。
7. **實際應用**：這個概念最後接回哪個裝置、決策或故障。
8. **可觀察證據**：用什麼看得到，以及它**不能**證明什麼。

公式、規則、參數只能在量與角色都說清楚之後才出現。

## 反模式

- 因為讀者某個領域很強，就假設他別的領域也懂。
- 用大量英文與縮寫製造專業感，卻沒有白話動作與層級位置。
- 把名詞解釋當概念解釋：只列定義，沒有角色、狀態、因果與證據。
- 比喻完就走，不回到真實機制，也不說比喻在哪裡失效。
- 先考後教：讀者還沒學會就要他判斷、選擇或診斷。
- 把典型值（某個門檻、某個建議秒數）講成萬用答案，不標假設與適用範圍。

- 卡在使用者（要他確認讀者基線、提供來源、拍板邊界）→ [WAIT_USER](../WAIT_USER.md) 一行；跨 session 的未完成節 → [SESSION-LOG](../SESSION-LOG.md) 一行；為什麼這樣簡化 → [decisions](decisions.md)。
